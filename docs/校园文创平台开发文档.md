## 1. 项目概述

### 1.1 项目背景

本项目为本校文创部定制开发的**文创产品展示与交易平台**，面向全校师生提供校徽徽章、纪念T恤、文创帆布袋、校园风景明信片等文创周边的浏览、搜索、预约与抢购能力。

**核心痛点**：校庆等重大活动期间，秒杀抢购瞬间会产生突发大流量，必须保证：
- 系统不因流量洪峰而宕机（可用性）；
- 分布式环境下**不超卖**、**一人一单**（交易稳定性）；
- 支付与订单状态在并发下保持一致（一致性）。

### 1.2 项目定位

- 文创产品 **展示 + 搜索 + 限时特惠抢购** 一体化平台；
- 内置 **AI 智能导购**（通义千问 + Function Calling），降低选购决策成本；
- 核心保障：**高并发不超卖、一人一单、最终一致**。

## 2. 技术栈与选型

| 类别 | 技术 | 版本 | 用途 |
| --- | --- | --- | --- |
| 开发语言 | Java | 17 | - |
| 框架 | SpringBoot | 3.2.x | Web 容器（WebMVC） |
| ORM | MyBatis-Plus | 3.5.x | 单表 CRUD + 分页插件 |
| 数据库 | MySQL | 8.0 | 业务数据持久化 |
| 缓存 | Redis | 7.x | 库存、验证码、Token、热点缓存、限流窗口、AI会话上下文 |
| 本地缓存 | Caffeine | 3.x | 商品详情一级缓存 |
| 消息队列 | Kafka | 3.x | 秒杀下单异步削峰、缓存删除失败重试 |
| 分布式锁 | Redisson | 3.x | 缓存重建锁、限流窗口（ZSet/RLock） |
| AI | LangChain4j + DashScope(通义千问 qwen-plus) | 0.33.x | 智能导购、Function Calling |
| 任务调度 | SpringTask (spring-boot-starter) | - | 未支付订单自动关单 |
| 鉴权 | JWT (jjwt) | 0.11.x | 无状态登录态 |
| 工具 | Lombok、Hutool | - | 简化开发、通用工具（日期/字符串） |
| 全局ID | RedisIdWorker（时间戳+自增序列） | - | 订单号等分布式唯一ID（见 6.1） |

### 2.1 选型理由

- **Kafka**：高吞吐、消息可持久化、支持消费重试与至少一次投递语义，适合秒杀削峰与缓存删除失败补偿。
- **Caffeine**：进程内缓存，读延迟微秒级，作为商品详情一级缓存极大降低 Redis 压力。
- **Redisson**：提供分布式锁 + ZSet 等现成数据结构，比手写 SETNX 更健壮（自动续期/看门狗）。
- **LangChain4j**：Java 侧统一 AI 抽象，`@Tool` 注解即可实现 Function Calling，屏蔽 DashScope API 细节。
- **MyBatis-Plus**：免写基础 SQL，聚焦复杂业务 SQL，降低开发成本。

### 3.3 核心设计决策速览

| 问题 | 决策 | 收益 |
| --- | --- | --- |
| 秒杀洪峰打垮下单接口 | 同步下单 → **Kafka 异步化** | 流量削峰，接口瞬时响应 |
| 并发超卖 | **Redis + Lua 原子预减库存** + DB 条件更新兜底 | 分布式下不超卖 |
| 同一用户抢多单 | Lua 内 Set 校验 + DB 唯一索引兜底 | 一人一单 |
| 热点 Key 集体失效（击穿） | Caffeine 兜底 + **Redisson 逻辑过期** + 锁内重建 | 击穿率归零 |
| 缓存与 DB 不一致 | 更新DB → 异步删缓存 → Kafka 重试 → **TTL 兜底** | 最终一致 |
| AI 需要实时数据 | **Function Calling** 动态调用库存/预约接口 | 回答可落地 |
| 刷单脚本/爬虫 | AOP + **滑动窗口限流**（按用户/IP/接口维度） | 拦截恶意流量 |
| 支付与关单竞争 | 订单**乐观锁（version/条件更新）** + 状态机 | 状态不串位 |

### 5.1 通用规范

| 500 | 系统异常 |
| 1001 | 验证码错误/过期 |
| 1002 | 用户不存在 |
| 2001 | 商品不存在或已下架 |

**鉴权方式**：登录后返回 JWT，请求携带 `Authorization: Bearer {token}`。登录拦截器放行 `/api/user/login`、`/api/user/send-code`、商品列表/详情、AI 对话等公开接口，其余需登录。

**登录拦截器（双拦截器 + Token 滑动续期）**

鉴权采用两个拦截器分工，职责单一：

| 拦截器 | 拦截范围 | 职责 | 校验失败 |
| --- | --- | --- | --- |
| RefreshTokenInterceptor | 全部请求（优先级1，先注册） | 解析 JWT → 查 Redis 会话 → 滑动续期 TTL → 写入 UserHolder(ThreadLocal) → **一律放行** | 仅不写入用户 |
| LoginInterceptor | 需登录的路径（优先级2） | 检查 UserHolder 中是否有用户 | 401 未登录 |

```
请求 ──► RefreshTokenInterceptor ──► LoginInterceptor ──► Controller
            │ 解析token + 续期              │ 校验ThreadLocal
            │ 放入UserHolder                │ 无用户 → 401
            └ 一律放行                      └ 有用户 → 放行
```

`RefreshTokenInterceptor` 核心：

```java
public class RefreshTokenInterceptor implements HandlerInterceptor {
    private final StringRedisTemplate redis;

    @Override
    public boolean preHandle(HttpServletRequest req, HttpServletResponse res, Object handler) {
        // 1. 取 token（Authorization: Bearer xxx）
        String token = req.getHeader("Authorization");
        if (StrUtil.isNotBlank(token)) {
            Long userId = JwtUtil.parseToken(token.replace("Bearer ", ""));
            if (userId != null) {
                String json = redis.opsForValue().get("login:token:" + userId);
                if (json != null) {
                    // 2. 会话有效：写入 ThreadLocal，并滑动续期 30min
                    UserHolder.saveUser(JSON.parseObject(json, UserDTO.class));
                    redis.expire("login:token:" + userId, 30, TimeUnit.MINUTES);
                }
            }
        }
        return true;                      // 3. 一律放行，真正的拦截交给 LoginInterceptor
    }

    @Override
    public void afterCompletion(HttpServletRequest req, HttpServletResponse res,
                                Object handler, Exception ex) {
        UserHolder.remove();              // 4. 防止 ThreadLocal 内存泄漏 / 请求间数据串号
    }
}
```

`LoginInterceptor` 核心：

```java
public class LoginInterceptor implements HandlerInterceptor {
    @Override
    public boolean preHandle(HttpServletRequest req, HttpServletResponse res, Object handler) {
        if (UserHolder.getUser() == null) {
            res.setStatus(401);           // 未登录
            return false;
        }
        return true;
    }
}
```

注册（WebMvcConfig）：

```java
@Configuration
public class WebMvcConfig implements WebMvcConfigurer {
    @Autowired private StringRedisTemplate redis;

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        // 1. 刷新拦截器：先注册，优先级高，拦所有
        registry.addInterceptor(new RefreshTokenInterceptor(redis)).addPathPatterns("/**");
        // 2. 登录拦截器：只拦需登录路径，放行公开接口
        registry.addInterceptor(new LoginInterceptor())
                .addPathPatterns("/**")
                .excludePathPatterns(
                    "/api/user/login", "/api/user/send-code",
                    "/api/category/**", "/api/product/**",
                    "/api/seckill/list", "/api/ai/**", "/error");
    }
}
```

> 说明：
> - **为什么登录态同时落 Redis 而不是纯 JWT**：JWT 无状态、签发后无法主动失效。这里把会话写入 Redis，拦截器每次请求滑动续期 TTL，登出时删除 Key 即可**立即踢下线**；
> - **ThreadLocal(UserHolder)**：在请求线程内共享当前用户，Service 层免去层层传参；`afterCompletion` 必须 remove，否则线程池复用线程时会把上一个请求的用户带进下一个请求；
> - 秒杀、订单、预约等敏感接口由 LoginInterceptor 兜底，未登录一律 401。

**分页参数**：`page`（页码，从1开始）、`size`（每页条数，默认10，最大50）。

**接口前缀**：所有接口以 `/api` 开头。

## 6. 核心功能详细设计

### 6.1 高并发秒杀设计（Kafka + Lua）

**目标**：秒杀洪峰不压垮 DB；不超卖；一人一单；下单接口毫秒级响应。

**两条链路对比**

```
【同步方案】请求 → 校验 → 扣库存(DB) → 建订单(DB)   → DB 直接承受全部并发，易超卖/宕机
【异步方案】请求 → Redis+Lua预扣 → 发Kafka → 立即返回 → 消费者异步落库   (削峰)
```

**下单时序**

```
用户 ──► Controller(校验随机码/活动时间)
         │
         ▼
Service ──► Redis EVAL  Lua(原子：一人一单 + 库存预减)
         │         │ 返回0=成功 1=重复 2=库存不足 3=活动非法
         │         ▼
         │    失败 → 直接返回错误
         │
         ▼
生成订单号(Redis时间戳+序列号) → Kafka 发送 seckill.order.topic
         │
         ▼ 立即返回 { orderNo, status:0 }
用户 ──► 轮询 /api/seckill/result/{orderNo} (纯Redis)
```

**Lua 脚本（完整）**

```lua
-- KEYS[1] = seckill:stock:{seckillId}     库存
-- KEYS[2] = seckill:buyers:{seckillId}    已购用户Set
-- ARGV[1] = userId
-- 返回：0成功 1已购 2库存不足 3活动不存在
if (redis.call('exists', KEYS[1]) == 1) then
    if (redis.call('sismember', KEYS[2], ARGV[1]) == 1) then
        return 1
    end
    local stock = tonumber(redis.call('get', KEYS[1]))
    if (stock <= 0) then
        return 2
    end
    redis.call('decrby', KEYS[1], 1)
    redis.call('sadd', KEYS[2], ARGV[1])
    return 0
end
return 3
```

> Lua 脚本整体在 Redis 单实例内原子执行，杜绝"检查-扣减"之间的竞态，从根源上避免超卖。

**异步消费者（Kafka）核心逻辑**

```java
@KafkaListener(topics = MqTopic.SECKILL_ORDER)
public void onSeckillOrder(SeckillOrderMsg msg) {
    // 1. 幂等：orderNo 唯一索引，重复消费直接失败
    // 2. 落订单：insert orders(status=0 待支付, version=0)
    // 3. 扣减 DB 秒杀库存（条件更新兜底）：
    //    update seckill_product set stock=stock-1
    //    where id=? and stock>0 and status=1
    //    影响行数=0 → 标记失败(回补 Redis 库存+移除买家)，写结果 seckill:order:{no}=2
    // 4. 写结果 seckill:order:{orderNo}=1(成功)
}
```

**防超卖 / 一人一单 双保险**

| 层级 | 手段 |
| --- | --- |
| 第一层 | Redis Lua 原子预减 + Set 判重（挡掉 99% 流量） |
| 第二层 | DB 条件更新 `stock>0`（极端兜底，行级锁语义） |
| 第三层 | `orders` 唯一索引 `(user_id, seckill_id)`（防重复落单） |
| 兜底 | 消费失败进入 Kafka 重试 + 死信 Topic 人工处理 |

**Redis 库存预热**：活动开始前，定时任务将 `seckill_product.stock` 写入 `seckill:stock:{id}`，并生成随机码 `seckill:code:{id}`。

**订单号生成（RedisIdWorker：符号位 + 时间戳 + 序列号）**

本项目订单号不采用雪花算法，而是使用 64 位 long，位结构定义如下：

```
64位 long（bit63 ~ bit0）
┌──────────────┬────────────────────────────┬──────────────────────┐
│  符号位 1 bit │  时间戳 31 bit（秒）        │  序列号 32 bit         │
│  恒为 0       │  相对 2022-01-01 的秒数     │  Redis 自增计数器      │
└──────────────┴────────────────────────────┴──────────────────────┘
```

- **符号位（1 bit）**：最高位 bit63，恒为 0，保证结果是正数（Java long 最高位为 1 则视为负数）；
- **时间戳（31 bit）**：以秒为单位，相对基准时间 `2022-01-01 00:00:00` 的秒数。`2^31` 秒 ≈ **68 年**，可一直用到约 **2090 年**；
- **序列号（32 bit）**：时间窗口内的计数器，理论上每秒可产生 `2^32`（约 42.9 亿）个不同 ID；本项目用 Redis 自增实现，实际远用不完。

```java
@Component
public class RedisIdWorker {
    private static final long BEGIN_TIMESTAMP = 1640995200L; // 基准时间：2022-01-01 00:00:00
    private static final int COUNT_BITS = 32;               // 低位序列号占 32 位

    private final StringRedisTemplate redis;

    public long nextId(String keyPrefix) {
        // 1. 时间戳：相对基准时间的秒数；左移 32 位后落在 bit32~bit62（31 bit），bit63 自动留作符号位
        LocalDateTime now = LocalDateTime.now();
        long timestamp = now.toEpochSecond(ZoneOffset.UTC) - BEGIN_TIMESTAMP;
        // 2. 序列号：Redis 按天自增，天然唯一、有序、趋势递增
        //    （若需精确"秒内计数器"，把日期后缀改为 yyyy:MM:dd:HH:mm:ss 即可）
        String date = now.format(DateTimeFormatter.ofPattern("yyyy:MM:dd"));
        long count = redis.opsForValue().increment("icr:" + keyPrefix + ":" + date);
        // 3. 拼接：时间戳左移 32 位，与序列号按位或
        return timestamp << COUNT_BITS | count;
    }
}
```

> 说明：
> - 代码里 `timestamp << 32 | count` 与位结构完全对应：bit63 符号位、bit32~bit62 时间戳（31 bit）、bit0~bit31 序列号；
> - 序列号**按天**自增时，同一秒内由 INCR 递增区分、不同秒由时间戳区分，组合 `(timestamp, count)` 全局唯一；改成**按秒**自增则每天/每秒序列从 1 重新开始，粒度更细；
> - 低 32 位不是 token，而是 **Redis `INCR` 自增序列号**，Redis 自增原子性保证并发下不重复、无需机器 ID；
> - 相比雪花算法：实现更简单、无时钟回拨问题，代价是每次生成有一次 Redis 网络开销（秒杀场景可接受）；
> - 对外存储时转成字符串写入 `orders.order_no`（VARCHAR(32)），5.4.3 响应中的 `orderNo` 即其字符串形式。

### 6.2 多级缓存设计（Caffeine + Redis）

**读路径**

```
查询商品详情 {id}
   ├─ Caffeine.getIfPresent → 命中返回（微秒级）
   ├─ 未命中 → Redis 逻辑过期检查
   │     ├─ 未过期 → 返回并回填 Caffeine
   │     └─ 已过期(逻辑) → 尝试获取 Redisson 分布式锁 lock:product:{id}
   │           ├─ 抢锁成功 → 查 DB → 写 Redis(带新逻辑过期时间) + Caffeine → 释放锁
   │           └─ 抢锁失败 → 返回旧数据（短暂过期，接受）
   └─ Caffeine 也未命中 → 直接查 DB 并回填两层缓存
```

**逻辑过期包装结构（关键防击穿点）**

```json
{ "data": { "id":1, "name":"校徽金属徽章", ... }, "expireTime": 1725xxxx }
```

- 缓存中**没有物理 TTL**，通过 `expireTime` 字段判断是否"逻辑过期"；
- 逻辑过期后**不删除** Redis Key，而是只让一个线程（持锁者）重建，其余线程返回旧数据；
- 彻底规避"热点 Key 失效瞬间大量请求穿透到 DB"的**缓存击穿**，同时配合 Caffeine 冷热分层进一步减压。

**缓存重建防并发（Redisson 锁 + 双检）**

```java
ProductVO p = caffeine.get(id);
if (p == null) {
    String json = redis.opsForValue().get(key);        // L2
    if (json == null) {
        RLock lock = redisson.getLock("lock:product:" + id);
        if (lock.tryLock(0, 30, TimeUnit.SECONDS)) {
            try {
                json = redis.opsForValue().get(key);   // 双检
                if (json == null) {
                    p = queryDbAndSetCache(id);         // 重建两层缓存
                    return p;
                }
            } finally { lock.unlock(); }
        }
        // 抢锁失败短暂自旋或直接回源一次（低概率）
    }
    p = parse(json);
}
return p;
```

**性能收益（压测目标值）**：单机 4C8G 下，商品详情接口 QPS 由 450 提升至 **2800**，DB 访问量下降 **89%**。

### 6.3 分布式一致性方案

**问题**：更新数据库后，若缓存删除失败，用户会读到脏数据。

**方案：更新DB → 异步删除缓存 → Kafka 重试 → TTL 兜底**

```
支付/改库存事务提交
   │
   ├─ 1. 删除 Redis 商品缓存（尽量先删缓存再更新DB，或更新后异步删，按场景选）
   ├─ 2. 删除 Caffeine 本地缓存（进程内，需在写入侧统一失效）
   │
   └─ 3. 若删除失败(网络抖动/超时) → 发 Kafka 延迟重试 Topic
           └─ 消费者重删缓存，最多重试 N 次，仍失败进死信
   └─ 4. 兜底：缓存带物理 TTL（如列表缓存 5min），最坏情况自动过期后重建
```

**一致性分级**

| 场景 | 策略 |
| --- | --- |
| 强一致要求（支付后金额） | 直接读 DB（订单相关） |
| 最终一致（商品详情/库存展示） | 删缓存 + Kafka 重试 + TTL 兜底 |

> 细节：写路径采用 **Cache-Aside**：先更新 DB，再删缓存。删除失败时通过 Kafka 消息重试，消息本身带版本号，消费者判断若版本已过则跳过，保证"删旧不删新"。

### 6.4 AI 智能导购（LangChain4j）

**架构**

```
用户消息 ──► ChatService
             ├─ Redis 拉取会话上下文(Hash，最近10轮)
             ├─ 组装 Messages + System Prompt
             ├─ 调用通义千问(qwen-plus)
             ├─ AI 判定需要实时数据 → 触发 Function Calling
             │     ├─ @Tool 查询实时库存   ──► ProductService
             │     └─ @Tool 查询预约进度   ──► ReservationService
             ├─ 将工具结果回传模型 → 生成最终回答
             └─ 回写上下文到 Redis(滑动窗口裁剪) + 返回
```

**Function Calling 工具定义（完整）**

```java
public class ProductTools {
    @Tool("查询指定文创商品的实时库存与价格，参数为商品ID")
    public String queryStock(@P("商品ID") Long productId) {
        Product p = productService.getById(productId);
        return "商品：" + p.getName() + "，当前库存 " + p.getStock() + "，售价 " + p.getPrice() + " 元";
    }
}

public class ReservationTools {
    @Tool("查询用户的文创预约进度，参数为预约ID，返回排队/制作中/可领取/已完成")
    public String queryProgress(@P("预约ID") Long reservationId) {
        Reservation r = reservationService.getById(reservationId);
        String[] dict = {"排队中", "制作中", "可领取", "已完成"};
        return "预约进度：" + dict[r.getProgress()];
    }
}
```

> LangChain4j 会把这些 `@Tool` 方法的 JavaDoc/注解描述转为模型的 function schema，模型在回答前自动决策"是否调用、传什么参数"，实现"AI 能查到真实库存/预约进度"的能力。

**带记忆的对话上下文**

- Key：`ai:session:{userId}:{sessionId}`（Hash：`role`→`content`，轮次编号）；
- 每次对话后追加，仅保留最近 10 轮，超出部分裁剪（控制 token）；
- 每次交互续期 TTL=30min；Redis 天然支持分布式，多实例无状态共享。

**同步 vs 流式**

| 模式 | 实现 | 适用 |
| --- | --- | --- |
| 同步 | `AiServices.chat`（阻塞返回完整回答） | 简单问答、测试 |
| SSE 流式 | `SseEmitter` + TokenStream `onPartialResponse` 逐段 `emitter.send` | 生产聊天体验 |

```java
@PostMapping("/chat/stream")
public SseEmitter chatStream(@RequestBody @Valid ChatReq req) {
    SseEmitter emitter = new SseEmitter(0L);           // 不超时
    TokenStream stream = aiService.stream(req.getSessionId(), req.getMessage());
    stream.onPartialResponse(part -> {
        emitter.send(SseEmitter.event().data("{\"delta\":\"" + part + "\"}"));
    }).onComplete(r -> {
        emitter.send(SseEmitter.event().data("[DONE]"));
        emitter.complete();
    }).onError(t -> emitter.completeWithError(t))
      .start();
    return emitter;
}
```

### 6.5 系统安全限流（AOP + 滑动窗口）

**自定义注解**

```java
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface RateLimit {
    int limit() default 10;        // 窗口内最大请求数
    int windowSeconds() default 60;// 窗口时长
    LimitDimension dimension() default LimitDimension.USER; // 用户/IP/全局
}
```

**滑动窗口算法（Redis ZSet 实现）**

```
窗口：60s，限流 10 次
每次请求：ZADD key score=now(毫秒) member=uuid
           ZREMRANGEBYSCORE key 0 (now-60s    ← 剔除窗口外旧请求
           count = ZCOUNT key (now-60s) +inf  ← 统计窗口内请求
           if count > limit → 返回 429
           else 放行（可对过期 key 设 TTL=窗口+1s 自动清理）
```

**AOP 切面核心**

```java
@Aspect
@Component
public class RateLimitAspect {
    @Around("@annotation(rateLimit)")
    public Object around(ProceedingJoinPoint pjp, RateLimit rateLimit) throws Throwable {
        String key = buildKey(rateLimit.dimension(), pjp);   // 拼接 用户ID/IP/接口路径
        Long now = System.currentTimeMillis();
        long winStart = now - rateLimit.windowSeconds() * 1000L;
        String zKey = "rate:limit:" + key + ":" + pjp.getSignature().getName();

        long count = redisScript.execute(滑动窗口Lua, zKey, now, winStart);
        if (count > rateLimit.limit()) {
            throw new BizException(429, "请求过于频繁，请稍后再试");
        }
        return pjp.proceed();
    }
}
```

**多维限流**

| 维度 | Key 前缀 | 应用 |
| --- | --- | --- |
| 用户维度 | `rate:limit:user:{userId}` | 防止同一账号刷单 |
| IP 维度 | `rate:limit:ip:{ip}` | 拦截爬虫/脚本 |
| 接口维度 | `rate:limit:api:{path}` | 秒杀、验证码等敏感接口总闸 |

**典型配置**：发送验证码 1次/60s、秒杀下单 3次/10s、商品详情 100次/60s、AI 对话 20次/60s。

> 补充建议：网关/负载均衡层再叠加一层全局限流（Nginx limit_req），纵深防御。

### 6.6 交易状态机管控（SpringTask + 乐观锁）

**订单状态枚举**

```
0 待支付 ──► 1 已支付 ──► 2 已发货 ──► 3 已完成
    │
    ├─(用户取消)→ 4 已取消
    └─(超时未支付)→ 5 已关闭
```

**自动关单（SpringTask 定时扫描）**

```java
@Component
public class OrderCloseTask {
    @Scheduled(cron = "0 */1 * * * ?")   // 每 1 分钟
    public void closeExpiredOrders() {
        // 分页扫描 status=0 且 create_time < now()-15min 的订单
        // 对每笔：乐观锁条件更新
        int rows = orderMapper.closeExpired(now);   // where status=0 and create_time<? and version=?
        if (rows > 0) { 回补库存; }
    }
}
```

**并发支付 vs 超时关单 的状态竞争（乐观锁解决）**

- 订单表引入 `version` 字段；
- 支付：`update orders set status=1, pay_time=now(), version=version+1 where id=? and status=0 and version=?`
- 关单：`update orders set status=5, version=version+1 where id=? and status=0 and create_time<?`
- 两次更新互相竞争，**只有一个能影响 1 行**（CAS 语义），输掉的一方拿到 0 影响行数 → 感知到状态已变 → 支付方提示"订单已关闭"，关单方不做多余回补。**状态机保证状态只允许单向流转，杜绝"支付成功后又被关单"的数据错乱。**

## 9. 常见问题排查

| 问题 | 原因 | 解决方案 |
| --- | --- | --- |
| 秒杀一直返回"库存不足"但 DB 还有货 | Redis 库存未预热 | 活动开始前跑预热任务，`seckill:stock:{id}` 必须存在 |
| 订单支付成功但商品缓存仍旧 | 删缓存失败 | 检查 Kafka `cache.delete.retry` 消费是否正常，TTL 兜底最坏 5min 恢复 |
| Kafka 消费重复导致重复下单 | at-least-once 语义 | 依赖 `orders` 唯一索引 `(user_id, seckill_id)` 幂等 |
| 热点商品详情偶发返回过期数据 | 逻辑过期策略设计如此 | 属预期：接受极短暂过期换取击穿率归零 |
| AI 不调用 Function Calling | 模型没识别意图 | 优化 @Tool 描述（写明用途/参数）；加大 System Prompt 引导 |
| 限流误伤正常用户 | 阈值过小 | 按维度分级配置，压测校准 |
| 关单任务重复回补库存 | 并发扫描 | 关单采用乐观锁条件更新，影响行数=0 则跳过 |
| 高并发下 Redis 单点瓶颈 | 热点集中在单 key | 库存 Key 可做分段分片；上线 Redis 集群 |

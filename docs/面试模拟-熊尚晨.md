## 第二轮：项目一 · 秒杀下单链路

> 这一轮是你简历的**主战场**，大概率占面试一半时间。建议把这轮的答案练到脱口而出。

### Q6. 先整体讲一下你的秒杀下单流程。

**这题是龙头，必须讲成一条清晰的链路：**

> 用户下单请求进来，依次经过五道关：
>
> **第一关，随机码校验。** 商品详情页会返回一个随机码，下单时必须带上。这个码存在 Redis，只有正常浏览过详情页的用户才能拿到，直接构造 URL 的脚本会被挡在门外。
>
> **第二关，Redis + Lua 原子预扣。** 一段 Lua 脚本里同时做两件事：判断用户是否已在已购集合里（一人一单），以及判断库存是否大于 0。两个判断和扣减、写入集合在 Redis 里是一条命令原子执行的，不存在中间状态。返回 0 表示预扣成功，1 是重复下单，2 是库存不足，3 是活动不存在。
>
> **第三关，生成全局唯一订单号**，用时间戳加 Redis 自增序列拼出来的，保证不重复。
>
> **第四关，预写"排队中"状态到 Redis**，轮询接口只读这个 key，绝不打 DB。
>
> **第五关，发 Kafka 消息**，key 用 `seckillId`，保证同一个活动的消息落到同一个分区、分区内有序。发完接口就返回排队号，毫秒级响应，落库交给消费者异步做。
>
> 整体思路就是**把能提前挡掉的流量挡在 Redis 这一层，把必须落库的动作异步化**。

---

### Q7. 为什么用 Lua 脚本？用 Java 分步执行不行吗？

> 不行，会有并发问题。如果我在 Java 里这么写：先 `sismember` 判断用户买没买过，再 `get` 判断库存，最后 `decr` 扣减——这三步之间其他线程可以插进来。
>
> 具体来说，用户 A 和用户 B 同时下单，两个线程都在 `sismember` 时查到"没买过"，然后都去扣库存，就变成一单卖给了两个人；库存只剩 1 件时，两个线程都读到 1，都判断 "> 0"，最后扣成 -1，就是超卖。
>
> Lua 脚本在 Redis 里是**整体原子执行**的，Redis 执行脚本期间不会插入其他命令，这三步天然串行。这是秒杀场景最干净的做法。

---

### Q8. Redis 执行 Lua 脚本期间真的不会有其他命令插进来吗？为什么？

**⚠️ 追问点，答不上来会显得是背的。**

> 不会。Redis 执行命令的是**单线程的事件循环**，Lua 脚本被当成"一条命令"提交给这个单线程执行，执行期间不会去处理其他客户端的事件。
>
> 补充一点边界：**这不代表整个 Redis 都卡死**。Redis 6.0 之后网络 IO 是多线程的，但命令执行仍然是单线程。另外如果脚本里有耗时操作，是会阻塞整个 Redis 的，所以 Lua 脚本里我只做 O(1) 的判断和扣减，绝不放循环和复杂查询。

---

### Q9. 你的 Lua 脚本第一行判断 `exists` 是什么意思？为什么放最前面？

> `exists` 判断库存 key 存不存在。不存在就返回 3，代表"活动不存在"。
>
> 放最前面是因为——**Redis 里的库存 key 是靠预热任务写的，DB 里有活动但 Redis 里没有，说明这个活动还没预热**。这时候如果放行，就会走到后面的 `get` 拿到 nil，`tonumber(nil)` 报错，或者被我错误地当成"库存充足"。
> 所以这行是个**兜底熔断**：宁可告诉用户"活动未开始"，也不能让没预热的流量穿过去。

**可以补一句加分**：这其实也保护了一个边界场景——`decrby` 在 key 不存在时会先创建为 0 再减成 -1，静默超卖。有了 `exists` 就堵住了。

### Q10. ⚠️ 库存预扣成功了，但 Kafka 消息发送失败，会怎么样？怎么解决？

**这题你代码里目前没处理，`kafkaTemplate.send` 的返回值没接收，也没有回调。必须准备。**

> 现在的实现里这是个**真实的缺口**：Redis 库存已经被扣掉 1 件，但消息没发出去，用户永远等不到订单，Redis 里的买家集合也留下了记录，用户重试会被判"重复下单"。结果是**这件商品卖不出去**——少卖。
>
> 解决思路有三层，从轻到重：
>
> **第一层，同步发送 + 失败回滚。** 用 `send().get()` 同步拿结果，失败就把 Redis 里的库存加回去、把用户从已购集合移除。缺点是同步阻塞，破坏了异步削峰的初衷，只能作为保底。
>
> **第二层，异步回调 + 补偿重试。** 给 `send` 加 `whenComplete` 回调，失败时把订单信息写进一张**本地消息表**（状态=待发送），由定时任务扫描重投。这是最常用的工业做法，代价是要多一张表。
>
> **第三层，事务消息。** RocketMQ 支持半消息 + 回查，能从根上解决。但我们现在用的是 Kafka，Kafka 原生不支持事务消息跨系统，硬做要自己实现回查逻辑。
>
> 另外还有个更简单的兜底：**Redis 里的库存和已购集合都设 TTL，或者用一个"预扣流水"记录带过期时间**，超时没收到消费确认就自动回补。这个方案实现成本最低，但一致性弱一些。

### Q11. ⚠️ Kafka 消费者怎么保证幂等？消息重复消费了怎么办？

**你代码里消费者还没实现。这题必答。**

> Kafka 的消息是**至少一次**投递语义，消费者重启、rebalance、或者处理完没来得及提交 offset 都可能重放，所以必须自己保证幂等。
>
> 我的做法是**在"订单号"上建唯一索引**，消费者落库时用 `INSERT IGNORE` 或者捕获唯一键冲突异常，冲突了就直接 ack，当成功处理。
> 为什么用订单号而不是用户 ID：订单号是 Redis 自增生成的全局唯一值，同一条消息重放多少次订单号都一样，天然适合做幂等键。
>
> 另外消费者端我还想加一层 Redis 的 `SETNX` 前置过滤——`setIfAbsent("consumed:" + orderNo, ...)`，抢不到就说明处理过了，直接返回，省掉一次 DB 往返。但**最终兜底一定要靠数据库唯一索引**，因为 Redis 可能丢数据。

### Q12. ⚠️ 为什么 Kafka 的 key 用 seckillId？用 userId 不行吗？不用 key 行吗？

> 用 `seckillId` 做 key，是为了**同一个活动的消息落到同一个分区**，分区内是有序的，保证库存扣减消息按顺序消费。
>
> 用 `userId` 的问题：同一个活动的消息会散到所有分区，多个消费者并行处理同一个活动的订单，虽然我在 Redis 已经扣过库存了，但如果消费者端还有任何依赖顺序的逻辑（比如生成连续的单号、或者按序写同一条记录），就会乱序。
>
> 不用 key 更糟：Kafka 默认用轮询（sticky）分区，消息随机落，完全无序。
>
> **不过这里有个取舍要说清楚**：用 `seckillId` 做 key 意味着**同一个热门活动只能被一个消费者线程处理**，吞吐上限就是这个单分区的处理能力。如果秒杀单活动的下单量大到单分区扛不住，就要考虑加分区 + 消费者端做分片键的重设计（比如按 `userId % N` 拆成子分区）。我们的场景是校庆秒杀，单活动峰值在万级，单分区足够。

### Q13. ⚠️ 一人一单用 Set 存已购用户，这个 Set 会无限增长吗？怎么清理？

**你代码里 `seckill:buyers:{id}` 没设 TTL，而库存 key 设了 24 小时。**

> 现在确实是个隐患。库存 key 有 24 小时 TTL，但已购集合 `sadd` 之后**没有设过期时间**，活动结束后这个 Set 里的元素会一直留在 Redis 里，活动多了就是内存泄漏。
>
> 修法：在 Lua 脚本里 `sadd` 之后顺手 `EXPIRE` 一次。因为 Lua 里改 key 的 TTL 是原子的，不会有窗口问题。过期时间设成"活动结束时间 + 一点缓冲"，比如 7 天，覆盖掉可能的补单和售后查询窗口。
>
> 更规范一点的做法是：**按活动维度存，key 带上活动 ID**（我现在就是），然后活动下线时由定时任务统一清理，这样比无脑 TTL 更可控。

**⚠️ 如果你改了代码，这里可以说"我后来补了 EXPIRE"——会显得你会自我 review。**

### Q14. ⚠️ 用户下单后一直没支付，库存怎么回补？

> 我现在**没有实现这个**，但完整方案我会这么做：
>
> 下单时在 Redis 里写一个**超时时间戳**，或者发一条**延迟消息**（Kafka 可以用时间轮 + 定时任务扫，或者用 RocketMQ 的延迟消息，再或者用 Redis 的 ZSet 做延迟队列）。
> 到点检查订单状态，如果还是"待支付"，就：DB 里把订单置为"已取消"，Redis 里 `incr` 把库存加回去，并且**把用户从已购集合里移除** `srem`。
>
> 这里有几个坑要注意：
> 一是**回补要和用户的下单请求互斥**，否则用户正在重新下单、库存刚加回去又被判定超时重复加，就超卖了。可以用 Lua 脚本把"检查状态 + 回补 + 移除买家"做成原子的。
> 二是**用户可能在超时瞬间刚好支付了**，所以要先命中 DB 的订单状态做最终判断（"更新成功并且影响行数=1"才算真的取消成功）。

### Q15. ⚠️ 你代码里 `listActive()` 在循环里逐个 `productMapper.selectById`，有问题吗？

**这是你代码里真实存在的 N+1 查询。**

> 有，这是典型的 **N+1 查询问题**。查出来 20 个秒杀活动，就要执行 1 次列表查询 + 20 次商品查询，总共 21 次数据库往返。
>
> 改法：先收集所有 `productId`，用一次 `selectBatchIds` 批量查出来，在内存里做成 `Map<Long, Product>`，然后循环里从 Map 取。这样就是 2 次查询。
>
> 如果连 Product 表都不想查，还可以考虑用一条 JOIN 的 SQL 直接查出 VO，但要权衡——JOIN 在数据量大时性能不如两次简单查询。我们这种数据量，批量查询更清晰。

### Q16. `listActive()` 里 `lt(beginTime, now.plusDays(3))` 这个条件是什么意图？有没有问题？

> 我的意图是只展示"未来三天内"的活动，避免把很久以后的秒杀也列出来。

### Q17. ⚠️ 你代码里 `detail()` 抛的是"活动预热中，请稍后再试"，为什么这么设计？用户会怎么想？

> 因为随机码是预热任务生成的，如果 Redis 里取不到码，说明活动还没预热——预热是每分钟扫一次的定时任务。
>
> 这有个**用户体验问题**：运营在后台新增一个秒杀活动，最坏情况下用户要等一分钟才能看到详情页。我当时的权衡是"宁可让用户等，也不能放过没预热的活动"。
>
> 更好的做法是：**运营后台新增活动时直接同步触发一次预热**（比如发个 MQ 事件），定时任务只作为兜底补偿。这样用户体验和安全性都保住了。

### Q18. 随机码真的能防住脚本吗？我把详情页拿到码，再拿去抢呢？

**⚠️ 这题是攻击性追问，不能只会说"能防"。**

> **防不住针对性脚本，但能抬高门槛。** 如果脚本作者先去请求详情页拿码，再带着码去下单，是可以通过的。
>
> 随机码真正的价值是**挡住"无脑刷接口"的脚本**：大部分刷单脚本是直接对下单接口加大并发，根本不走详情页，这类会被 100% 拦截。
>
> 要防针对性脚本，得组合拳：
> 一是**把随机码和用户绑定**，比如 `seckill:code:{id}:{userId}`，让码不能转让；二是**加上验证码或滑块**，走人机校验；三是**AOP 限流**（我在项目里实现了），限制单用户单位时间的请求数；四是**风控**，识别同 IP 段、同设备指纹的批量请求。
>
> 我的定位很清楚：随机码是第一道便宜的过滤网，真正拦得住恶意流量还得靠限流和风控。

### Q19. 轮询接口为什么要走 Redis 不走 DB？

> 两个原因。一是**轮询的量级远大于下单量**——用户下单后可能每秒轮询一次，持续十几秒，一个用户就是十几次请求；而 Redis 的 QPS 是 DB 的几十倍，这个量级只有 Redis 扛得住。
> 二是我把**状态和订单数据一起序列化进了 Redis 的 value 里**，轮询接口一次 `GET` 就能返回完整结果，不需要再去查 DB 补数据。
>
> 加上 10 分钟的 TTL，用户拿到结果或放弃之后 key 自动清理，不会长期占用内存。

---

### Q20. ⚠️ 轮询其实也是压力。有没有更好的方案？

> 有，轮询本质上是**用客户端的无效请求换服务端的实现简单**。
>
> 更好的方案：
> **一是长轮询**，服务端 hold 住请求，有结果了再返回，能减少大量空轮询；但要占用容器线程，数量大了要换异步 Servlet。
> **二是 SSE（Server-Sent Events）**，服务端单向推送，浏览器原生支持，特别适合"下单结果通知"这种场景，实现也简单。
> **三是 WebSocket**，全双工，但要维护连接状态，对秒杀这种一次性通知有点重。
>
> 如果让我选，我会用 SSE——单向推送正好匹配这个场景，比 WebSocket 轻，比轮询省资源。

---

### Q21. 你的订单号是怎么生成的？为什么不用 UUID？

> 用的是**时间戳左移 + Redis 自增序列**的雪花式算法（`RedisIdWorker`）。
>
> 具体是：用当前秒级时间戳减去一个起始时间点，左移 32 位，低位放 Redis 的 `INCR` 自增序列，这样同一个秒内最多能生成 2^32 个不重复 ID。
>
> 不用 UUID 的原因：**UUID 是无序的，做主键会导致 B+ 树页分裂严重，插入性能差**；而且 36 个字符占空间，比 long 大得多。
> 雪花算法本身依赖机器 ID，我们这里用 Redis 的 `INCR` 代替，好处是**不依赖机器时钟，也就不用处理时钟回拨问题**——代价是多一次 Redis 往返。

---

### Q22. 那如果 Redis 挂了，订单号还能生成吗？

> 不能，这是这个方案的**单点依赖**。
>
> 几个应对方向：一是 Redis 做主从 + 哨兵保证高可用，故障时自动切换；二是加**本地兜底**，Redis 不可用时降级成"时间戳 + 进程内 AtomicLong + 机器标识"的本地生成，虽然可能重复但能保证服务不完全不可用；三是业务层面接受短暂不可用——秒杀本来就是个短时活动，宁可停一下也不要生成重复订单号。
>
> 我倾向于**选三 + 一**：Redis 高可用保证了绝大部分情况，真挂了就快速失败，因为重复订单号的后果比服务短暂不可用严重得多。

---

### Q23. 秒杀开始那一瞬间，所有请求都打同一个 Redis 库存 key，这是不是热点问题？

**⚠️ 好问题，能答上来很加分。**

> 是，`seckill:stock:{id}` 是个**超级热 key**，所有请求都读写同一个 key。单个 Redis 节点的处理能力有限，这个 key 会成为瓶颈。
>
> 解决方案是**库存分片**：把库存拆成 N 份，比如 100 件拆成 10 个 key，每个 10 件，key 带上分片号。用户请求按 `userId % N` 路由到某个分片，Lua 脚本在这个分片上扣减，扣成功了再拼上分片号去下单。
> 这样就把单 key 的压力分散到 N 个 key，Redis 集群下还会落到不同节点。
>
> 代价是**可能出现"有的分片空了但别的分片还有货"**，导致少卖。可以在一个分片扣失败时轮询其他分片重试，或者接受这点损失——秒杀场景下少卖比超卖好。
>
> 除了分片，还可以考虑**本地库存 + Redis 兜底**的两级扣减，进一步减少 Redis 压力。

---

### Q24. 你在 Lua 里用了 `KEYS[1]` 和 `KEYS[2]`，为什么不像限流那样直接拼字符串？

> Redis 的 `EVAL` 命令要求**所有操作的 key 都通过 `KEYS` 数组传**，而不是在脚本里硬编码或拼字符串。
>
> 原因是 **Redis Cluster 需要提前知道这个脚本要操作哪些 key，才能判断它们是否在同一个槽位（slot）**。如果 key 都散在不同节点上，脚本没法原子执行，集群会直接报错。
>
> 所以规范做法就是：**key 一律走 `KEYS`，参数一律走 `ARGV`**。我的 `seckill.lua` 里两个 key 都是 `KEYS`，`userId` 是 `ARGV`，符合规范。
>
> 顺便提一句取舍：**集群下如果要保证多个 key 在同一个节点，需要用 hash tag**，比如 `{seckill:1}:stock` 和 `{seckill:1}:buyers`，大括号里的内容相同就会路由到同一个槽。我的两个 key 恰好都用 `seckillId` 结尾，是幸运而不是设计——如果要上集群，我应该显式加上 hash tag。

---

### Q25. 为什么库存预扣成功后要给结果写一个"排队中"的 key，而不是直接返回成功？

> 因为**异步下单还没落库**。如果直接返回"下单成功"，用户拿着订单号去查订单，DB 里还没有，体验就崩了。
>
> "排队中"这个状态给了前端一个明确的语义：**已受理，但结果未定**。前端拿到排队号后去轮询结果接口，轮询到状态变成 1（成功）或者 2（失败）再展示。
>
> 这本质上是我把**同步的请求-响应模型改造成了异步的受理-通知模型**，这是削峰架构的必然代价。

---

### Q26. 你的 `getResult` 做了 `userId` 校验，为什么？

> 防止**水平越权**。订单号是可以被猜测或者遍历的，如果不校验归属，攻击者拿一串订单号去查，就能看到别人的订单信息。
>
> 我在 `SeckillResultVO` 里存了 `userId`，查询时对比当前登录用户，不一致就返回 403。这比单纯依赖订单号不可猜更可靠。
>
> 更进一步的做法是把 `userId` 直接编进 Redis 的 key 里，比如 `seckill:order:{userId}:{orderNo}`，这样从 key 层面就隔离了，但要注意 key 的设计会影响清理和维护成本。我觉得当前方案够用。

### Q27. 秒杀接口的 TPS 大概是多少？你压测过吗？怎么压的？

**⚠️ 简历写了 "QPS 由 450 提升至 2800"，这题必然被追，必须能说清压测环境。**

> 压测用的是 JMeter。场景是 200 个并发线程，持续压 1 分钟，测的是商品详情接口——因为那是流量最大的读接口。

> 环境说明一下：**是本地单机环境**，MySQL 和 Redis 都在本机，所以这个数字是相对的——它说明的是**优化前后的倍率**，不是生产环境的绝对值。

> 如果要更严谨，我应该补充 P99 响应时间、错误率，以及在不同并发梯度下的表现（比如 50/100/500 并发分别测），这样能看出系统在哪个点开始劣化。这个我后面补测过一版，印象里在 400 并发左右 QPS 开始不再线性增长。

### Q28. 如果让你重新设计这个秒杀系统，你会改什么？

### Q29. Lua 脚本里如果 `sadd` 成功但 `decrby` 失败了会怎样？

> 不会发生。Redis 的 Lua 脚本**整体原子**，脚本中途报错的话，**已经执行过的写命令不会回滚**——这是 Redis 和数据库事务的重要区别。
>
> 但在我这个脚本里，`decrby` 和 `sadd` 都是简单命令，只要 key 类型对就不会失败。而且我把 `decrby` 放在 `sadd` 前面，是因为**库存扣减是更关键的语义**——真出现异常，我更希望是"库存扣了但买家没记上"（少卖，用户重试可能被放过）而不是"买家记上了但库存没扣"（超卖风险）。
>
> 不过更严谨的写法是**把 `sadd` 放前面**：这样异常时是"记了买家但没扣库存"，用户会被告知重复下单，绝对不会超卖。我现在的顺序其实是**优先保证用户体验、承担了可控的超卖风险**——如果要严格保证不超卖，应该反过来。

**⚠️ 这题很深，如果你答不上来就说"我需要再想一下"，不要硬编。** 能答上来可以直接拉开差距。

### Q30. 为什么不直接用数据库的 `UPDATE ... WHERE stock > 0` 扣库存？那不是天然原子吗？

> 可以，这是最朴素的方案，`UPDATE seckill_product SET stock = stock - 1 WHERE id = ? AND stock > 0`，靠行锁保证不超卖。
>
> 但问题是**性能**。所有请求都在同一行上竞争行锁，等于把并发串行化了，还要走网络往返到 DB。秒杀场景下几千 TPS 打到 MySQL 单行上，直接就把 DB 拖垮了。
>
> Redis 的方案是把**竞争下沉到内存**，Redis 单机就能扛十万级 QPS，成本低一个数量级。
>
> 当然 Redis 方案引入了新问题：**Redis 和 DB 的库存怎么保持一致**。我的处理是"Redis 只做预扣的闸门，DB 是最终账本"，DB 的扣减在消费者里用 `UPDATE ... WHERE stock > 0` 做二次校验——**Redis 挡流量，DB 保正确**，两层都防超卖。

---

### Q31. 那 DB 的二次校验失败了怎么办？Redis 说还有货，DB 说没了。

> 这种情况说明**Redis 和 DB 的库存不同步了**，通常是 Redis 被误覆盖（比如预热任务用了 `set` 而不是 `setIfAbsent`）或者人工改了 DB 库存。
>
> 处理方式：消费者发现 DB 扣减影响行数为 0，就把订单标记为失败，**同时把 Redis 的库存回补**（`incr`）并移除已购记录，让用户可以重试。同时打**告警日志**，因为这个状态本身就不正常，需要人工介入排查。
>
> 预防上：预热任务我用的是 `setIfAbsent` 而不是 `set`，就是防止把已扣减的库存覆盖回去——这个细节我在代码注释里专门写了反例。

### Q32. 秒杀活动结束后 Redis 里的数据怎么处理？

> 分几类：
> **库存 key 和随机码**：设了 24 小时 TTL，自动过期。
> **已购用户集合**：现在是**没有 TTL 的，这是个已知缺陷**，应该补上按活动结束时间 + 缓冲期设置的过期。
> **排队结果 key**：10 分钟 TTL，用户轮询完就自然清理。
> **限流用的 ZSet**：每次访问都会 `PEXPIRE` 续期，窗口过后自动消失。
>
> 整体策略是**尽量靠 TTL 自动清理，减少人工干预**，但对没设 TTL 的 key 要有清理任务兜底。

## 第三轮：项目一 · 多级缓存与一致性

### Q33. 讲一下你的多级缓存是怎么设计的。

> 商品详情页做了 **Caffeine（本地缓存）+ Redis（分布式缓存）两级**。
>
> 请求进来先查 Caffeine，命中就直接返回，不走网络；没命中查 Redis；Redis 也没有才查 DB 并回填。
>
> Caffeine 作为一级缓存的价值在于**省掉网络往返**——本地内存访问是纳秒级，Redis 是毫秒级，差了两三个数量级。对于爆款商品详情这种超高读的热点数据，本地缓存能挡掉绝大部分请求。
>
> 但代价是**集群环境下每台机器的本地缓存是独立的**，数据更新时各节点不一致，所以我又用了逻辑过期来处理缓存的时效问题。

---

### Q34. Caffeine 和 Redis 都存在的时候，数据不一致怎么处理？

> 这是多级缓存的固有代价，我的处理是**接受短暂不一致，用逻辑过期 + 异步重建来控制窗口**。
>
> 具体来说，本地 Caffeine 我设的过期时间比 Redis 的**逻辑过期时间短一些**，这样本地过期后会自动回源到 Redis 拿较新的数据，Redis 逻辑过期后才会触发重建。
>
> 如果要求强一致，那就得做**缓存变更广播**——数据更新时通过 Redis 的发布订阅或者 MQ 通知所有节点删本地缓存。但这会引入新的复杂度，对商品详情这种**读多写极少**的场景不值得。
>
> 我的判断标准是：**容忍度是由业务决定的**。商品名字改了晚 5 秒生效没人有意见，但库存晚 5 秒生效就是要命的，所以库存我根本不走本地缓存，直接走 Redis + Lua。

---

### Q35. 什么是逻辑过期？为什么能解决缓存击穿？

> **缓存击穿**指的是某个热点 key 突然失效，同一时刻大量请求发现缓存没了，全部涌向 DB，瞬间把 DB 打垮。
>
> 常规解法是**互斥锁**：只让一个线程去查库重建，其他线程等待。但等待就意味着请求被阻塞，热点 key 下会有大量线程排队，响应时间飙升。
>
> **逻辑过期**换了个思路：**key 永不设物理 TTL，过期时间写在 value 里面**。请求读到数据后先看 value 里的 `expireTime`，如果没过期直接返回；如果过期了，**当前请求立即返回旧数据，同时异步去重建缓存**。
>
> 好处是所有请求**零阻塞**——没有线程在等锁，最多拿到的是稍旧的数据。坏处是**牺牲了强一致性**，会有一段时间返回旧值。
>
> 秒杀商品详情这种"读多写少、对短暂陈旧不敏感"的场景，用逻辑过期比互斥锁更合适。如果对一致性要求高，那就得用互斥锁，让请求等一下。

---

### Q36. ⚠️ 你的异步重建线程池为什么要用 `CallerRunsPolicy`？这不会阻塞主线程吗？

**这是个很好的追问点，你的注释里已经写了答案。**

> `CallerRunsPolicy` 的意思是：**当线程池和队列都满了，由提交任务的那个线程（也就是处理用户请求的 Tomcat 线程）自己执行这个任务**。
>
> 会阻塞主线程，但这是**有意的降级**。对比其他拒绝策略：
> - `AbortPolicy` 直接抛异常，用户收到 500，体验更差；
> - `DiscardPolicy` 静默丢弃，缓存永远不会重建，数据永远是旧的，最危险；
> - `DiscardOldestPolicy` 丢掉队列里最老的任务，同样是丢任务。
>
> `CallerRunsPolicy` 是**唯一一个"不丢任务、不抛异常"的策略**——代价是降级回同步重建，慢一点，但数据一定能更新。宁可慢，不可错。
>
> 补充一下参数依据：核心 2 线程、最大 4、队列 100。重建是**低频 IO 任务**，每个 key 逻辑过期才触发一次，正常情况下并发很低。队列 100 是为了缓冲"多个 key 同时过期"的突发。

---

### Q37. 那如果缓存重建慢，`CallerRunsPolicy` 把 Tomcat 线程都占满了呢？

**⚠️ 攻击性追问，这题答好了非常加分。**

> 这是这个方案的**真实风险**——如果 `dbFallback` 的查询特别慢，Tomcat 线程池会被拖垮，导致整个服务不可用。相当于**局部故障扩散成全局故障**。
>
> 三个改进方向：
> **一是给重建加超时**，比如 `dbFallback` 内部用 `Future.get(timeout)` 包一层，超时就放弃重建、记录日志，让请求快速返回旧数据。
> **二是隔离线程池**，重建用的线程池和业务线程池不能是同一个，现在虽然分了池但 `CallerRunsPolicy` 又把它们拉回来了。可以改成**记录失败 + 交给单独的补偿任务重试**，而不是让 Tomcat 线程去跑。
> **三是加熔断**，如果重建连续失败 N 次，就暂时停止重建，避免持续打 DB。
>
> 我现在的实现是"简单优先"，如果这个接口的 SLA 要求高，我会选第一种：**给重建加超时，超时就返回旧数据**——毕竟逻辑过期方案的整个前提就是"旧数据可接受"。

---

### Q38. 逻辑过期方案里，数据的 key 永不删除，内存不会爆吗？

> 确实有这个风险，这是逻辑过期用**内存换可用性**的代价。
>
> 我的应对是**控制缓存的数据范围**：只缓存热点的、有限的商品数据，不是全表缓存。而且缓存重建时如果发现商品已经下架（`dbFallback` 返回 null），我会**主动 `delete` 这个 key**，避免永远返回旧数据。这段逻辑在我代码里是有的。
>
> 如果数据量确实大，还有几个办法：一是**冷热分离**，只对访问量 Top N 的商品做逻辑过期，其余走普通 TTL 缓存；二是**定期扫描清理**，用定时任务找出长期未访问的 key 删掉；三是**限制单 key 的 value 大小**，避免存超大对象。
>
> 另外业务上，商品详情本身是有生命周期偏短的，配合活动下线的清理任务，实际内存占用是可控的。

---

### Q39. ⚠️ 你的 `CacheClient` 里，异步任务抢锁失败就直接 return 了，会不会导致缓存永远不更新？

> 有理论上的可能，但实际影响很小，我说明一下判断依据。
>
> 抢锁失败意味着**已经有另一个线程在重建这个 key 了**，那个线程重建完会写入新数据和新过期时间，所以缓存最终会被更新。这里不存在"没人重建"的情况。
>
> 真正的边界是：**如果抢到锁的那个线程重建失败了**（比如查库抛异常，或者进程刚好被杀），那这次重建就丢了，缓存会一直是旧数据，直到下一次有请求命中这个过期 key 才会再触发重建。
>
> 所以我的兜底是：**只要还有流量访问这个 key，就会被反复触发重建**，不会永久陈旧。另外我在异步任务里 `catch` 了所有异常并记了 error 日志，避免异常无声消失——异步线程的异常没人接住是最容易埋雷的地方。
>
> 如果要更严谨，可以给锁加 TTL + 失败重试计数，连续失败就告警。

---

### Q40. 为什么 Redisson 的锁必须加锁和解锁在同一个线程？

> 因为 Redisson 的 `RLock` 是**可重入锁**，它需要在 Redis 里记录"**是哪个线程持有这个锁、重入了多少次**"。这些信息用一个 Hash 存储，field 是"客户端ID:线程ID"，value 是重入计数。
>
> 解锁的时候，它要先判断"当前线程是不是锁的持有者"，不是就直接抛 `IllegalMonitorStateException`。所以主线程加锁、子线程解锁必然报错。
>
> 我代码里原来的写法是主线程 `tryLock`、工作线程 `unlock`，就是这么踩的坑。**最后的解法是把整个"抢锁 + 查库 + 写回 + 解锁"打包丢进线程池**，让加锁和解锁都发生在工作线程里。这个约束直接决定了我的代码结构。
>
> 顺便一提，如果用 `RedissonClient.getLock()` 的**非可重入锁** `getLock` 其实还是可重入的，要真正非重入得用 `getLock` 的重载或者别的锁类型，但根本问题还是"锁的持有者按线程标识"这个设计。

### Q41. 缓存穿透、击穿、雪崩，分别是什么？你怎么处理的？

**必考八股，但要用自己的项目串起来。**

| 问题 | 定义 | 你的方案 |
|---|---|---|
| **穿透** | 查一个**根本不存在**的数据，缓存永远不命中，每次都打 DB | 缓存空值 / 布隆过滤器 |
| **击穿** | **单个热点 key 突然失效**，大量请求同时打 DB | **逻辑过期 + 异步重建**（你已实现）|
| **雪崩** | **大量 key 同时失效**，或者 Redis 整体宕机 | TTL 加随机值 / 多级缓存 / 熔断降级 |

> 展开说：
> **穿透**我目前没有专门处理，如果要加，最简单的方案是**缓存空对象**——查不到也往 Redis 写一个空值，设短一点的 TTL（比如 60 秒）。但要注意如果攻击者用大量随机 ID 来刷，会往 Redis 里写满无用的空 key，那就得改用**布隆过滤器**，把所有存在的商品 ID 预加载进去，不存在的直接挡在缓存前面。
>
> **击穿**就是我用逻辑过期解决的核心问题，见前面的说明。
>
> **雪崩**我这边有两个天然的抗性：一是**多级缓存**，Redis 挂了 Caffeine 还能顶一层；二是**逻辑过期的 key 不设物理 TTL**，不存在"同一时刻集体失效"的问题。如果要再加，就是给普通缓存的 TTL 加随机扰动，比如原本 30 分钟，改成 30 分钟 ± 5 分钟的随机值。

### Q42. 订单支付后你是怎么保证缓存一致的？"更新数据库 + 异步删除缓存"具体怎么做？

> 这是 **Cache Aside 的变体**，核心取舍是"**先更新 DB，再删缓存，删失败就异步补偿**"。
>
> 流程是：支付成功后先更新 DB，然后**删除**对应的缓存（注意是删除而不是更新——更新的问题在于并发下可能写入旧值），删除动作通过 Kafka 异步发出去。
>
> 为什么要异步：**同步删缓存会给支付接口增加一次 Redis 往返和失败风险**，支付是核心链路，不能让缓存的问题影响它。
>
> 删失败怎么办，我做了两层兜底：
> **一是 Kafka 消息重试**，消费失败会重投，直到删成功（幂等，删两次没副作用）。
> **二是 TTL 兜底**，即使重试全部失败，缓存最终也会过期，保证最终一致。
>
> 为什么不先删缓存再更新 DB：**先删缓存的话，删完到 DB 更新完成之间有个窗口**，这段时间读请求会把 DB 里的旧值又加载回缓存，导致缓存长期是旧数据。**先更新 DB 再删缓存，脏数据的窗口更小**。

---

### Q43. "先更新 DB 再删缓存"真的没问题吗？有没有反例？

**⚠️ 深水区，答上来直接拉分。**

> 严格说**有问题**，只是概率低。经典反例是：
> 请求 A 要更新数据，请求 B 要读数据。
> 1. B 读缓存，未命中
> 2. B 读 DB，拿到旧值
> 3. A 更新 DB 成功，删除缓存
> 4. B 把**旧值**写入缓存
>
> 结果缓存里是旧值，而且可能长期存在。要触发这个需要 B 在"读 DB"到"写缓存"之间卡很久，概率极低——这也是为什么工业界普遍接受这个方案。
>
> **缓解手段有**：一是**延迟双删**，更新 DB 删缓存后，延迟几百毫秒再删一次，把那个窗口里可能被写回旧值的缓存再清一遍；二是**给缓存设较短 TTL**，让脏数据自己过期；三是**用 Canal 订阅 binlog**，数据库变更后由独立组件删缓存，彻底和业务解耦。
>
> 我的项目里用的是**删除 + Kafka 重试 + TTL 兜底**这个组合，没有做延迟双删。如果对一致性要求更高，我会加上延迟双删——成本很低，就是多一次删除。

---

### Q44. 为什么更新缓存用"删除"而不是"更新"？

> 两个原因：
>
> **一是并发下会写坏数据。** 假设两个线程几乎同时更新，A 先算好新值、B 后算好新值，但 B 的网络快先写入缓存，A 后写入——缓存里最终是 A 的旧值，而 DB 里是 B 的新值。删除就没这个问题，删掉之后下次读自然从 DB 加载最新的。
>
> **二是"更新"是懒加载的浪费。** 如果这个数据更新后根本没人读，更新缓存就是白做一次计算和写入。删除是**惰性的**——只有真正有人读了才回填，更省资源。

---

### Q45. 你的 Caffeine 缓存是怎么配置的？为什么这么配？

> 我配了**最大容量和过期时间**两方面。
> 容量限制是必须的——本地缓存占的是 JVM 堆内存，不设上限容易 OOM。
> 过期时间上，我设的比 Redis 短，让它自动回源到 Redis 拿较新的数据，形成"本地过期 → 回源 Redis → Redis 逻辑过期则重建"的层次。
>
> Caffeine 相比 Guava Cache 的优势是**用了 Window TinyLFU 淘汰算法**，命中率比 LRU 高——LRU 的问题是偶发的批量扫描会把热点数据挤出去，而 TinyLFU 会统计访问频率，能保护真正的热点。

---

### Q46. 如果让你在集群环境下保证 Caffeine 的一致性，你会怎么做？

> 三个方案，按复杂度递增：
>
> **一是缩短本地 TTL。** 最简单，把不一致窗口控制在几秒内。适合对一致性要求不极端的场景，成本为零。
>
> **二是广播失效。** 数据更新时通过 **Redis 的 Pub/Sub** 或者 **MQ 广播消息**通知所有节点，各自删掉本地缓存。要注意 Pub/Sub 是**不保证送达**的（没有持久化），所以还得配合 TTL 兜底。
>
> **三是集中式方案。** 干脆不用本地缓存，全部走 Redis，用 Redis 集群扛量。牺牲一部分性能换一致性。
>
> 我的选择逻辑是：**先问业务能容忍多旧的数据**。商品详情几秒可接受，就用方案一；如果是配置类的、要求准实时的，用方案二；如果是金额、库存这类绝对不能错的，直接用方案三或者干脆不缓存。

## 第四轮：项目一 · AOP 限流与安全

### Q47. 讲一下你的限流是怎么实现的。

> 用 **AOP + 自定义注解 + Redis 滑动窗口**实现的。
>
> 先定义一个 `@RateLimit` 注解，可以配三个参数：**限流维度**（用户 / IP / 接口）、**窗口时长**、**窗口内最大请求数**。
>
> 然后写一个 `@Around` 环绕通知的切面，拦截所有标注了 `@RateLimit` 的方法。切面里先根据维度算出限流的身份标识，拼成 Redis 的 key，然后执行一段 **Lua 滑动窗口脚本**，返回 1 表示放行、0 表示拒绝，拒绝就抛 429 异常。
>
> 放行的话才 `proceed()` 执行真正的业务方法。
>
> 这样业务代码里只要加一行注解就能限流，**限流逻辑和业务逻辑完全解耦**，这是 AOP 最典型的使用场景。

---

### Q48. 滑动窗口的 Lua 脚本具体是怎么实现的？

> 用 **ZSet（有序集合）**实现，member 是每个请求的唯一标识，score 是请求的时间戳。
>
> 三段逻辑：
> **第一步，`ZREMRANGEBYSCORE` 清理窗口外的数据**——把 score 小于"当前时间 - 窗口时长"的成员全部删掉，剩下的就是当前窗口内的请求。
> **第二步，`ZCARD` 统计窗口内的请求数**，如果已经达到上限，返回 0 拒绝。
> **第三步，`ZADD` 把当前请求加进去，然后 `PEXPIRE` 设置 key 的存活时间**，闲置后自动清理。
>
> 三步放在一段 Lua 里，**保证原子性**——否则"统计"和"添加"之间会有并发窗口，导致限流不准。

---

### Q49. 为什么不用固定窗口？滑动窗口好在哪？

> **固定窗口**是最简单的方案：直接用 `INCR` 计数，key 是"用户ID + 当前分钟"，超过阈值就拒绝，key 每分钟自动过期。
>
> 它的问题在**窗口边界**：比如限制每分钟 100 次，用户在 00:59 打了 100 次，01:00 又打 100 次，**两秒内实际通过了 200 次**，是阈值的两倍。这叫"窗口临界问题"，对刷单脚本来说这个漏洞是可利用的。
>
> **滑动窗口**是"从现在往前推 60 秒"这个动态区间，不存在固定边界，任何时刻往前看 60 秒都严格不超过阈值。
>
> 代价是**需要存储每个请求的时间戳**（ZSet 的成员），内存占用比一个计数器大得多，操作也是 O(logN) 而不是 O(1)。所以**对精度要求不高的接口用固定窗口就够了，只有防刷这种关键接口才用滑动窗口**。

---

### Q50. 令牌桶和漏桶了解吗？和滑动窗口什么区别？

> 了解，这两种解决的是不同的问题。
>
> **令牌桶**：以恒定速率往桶里放令牌，桶有容量上限。请求来了要拿一个令牌，拿不到就拒绝。特点是**允许突发流量**——桶里攒了 100 个令牌，突然来 100 个请求可以一次性全部通过。
> **漏桶**：请求先进桶，以**恒定速率**流出。不管进来多少，出去的速率是固定的，超出的排队或丢弃。特点是**绝对平滑**，适合保护下游有固定处理能力的系统。
> **滑动窗口**：单纯统计"时间窗口内的请求数"，不允许超出阈值，也不做排队。
>
> 区别总结：**令牌桶允许突发、漏桶强制平滑、滑动窗口严格控制数量**。
>
> 秒杀防刷场景我选滑动窗口，因为我的目的是"**严格控制单位时间内单个用户能发多少请求**"，不允许突发——刷单脚本就是要用突发流量打垮你。如果要保护下游 DB，漏桶更合适；如果要兼顾正常用户的突发操作，令牌桶更友好。

---

### Q51. ⚠️ 你的限流 key 里用了 `UUID.randomUUID()` 做 member，有什么问题？

**你代码里的真实设计，值得反思。**

> 用 UUID 是为了保证**每个请求在 ZSet 里的成员唯一**——如果只用时间戳，同一毫秒的多个请求会覆盖成同一个成员，计数就少了。
>
> 但代价是**ZSet 里存了大量无意义的 UUID 字符串**。按窗口 60 秒、限流 100 次算，每个用户最多 100 个成员，每个 UUID 36 字节，加上 ZSet 本身的开销，一个用户大概几 KB。用户量一大，Redis 内存压力很明显。
>
> 优化方向：**可以用 `时间戳 + 自增序列` 或者直接用请求的 traceId 代替 UUID**，长度短一些。更好的是**不用 ZSet 存明细**——如果只是要"不超阈值"，可以把窗口切成若干小格（比如 60 秒切成 6 个 10 秒的格子），只存每格的计数，内存从 O(请求数) 降到 O(格子数)，代价是精度变成格子粒度。
>
> 要不要优化取决于业务量。校庆这种短时活动，用户量有限，现在的实现完全够用；如果是全站级别的限流，就必须优化。

---

### Q52. 你的限流是分布式的吗？多台机器部署会怎样？

> 是分布式的，因为**计数存在 Redis 里，多台机器共享同一个 key**。不管请求打到哪台机器，看到的是同一个窗口计数，这是用 Redis 做限流的天然好处。
>
> 对比**单机限流**（比如 Guava 的 `RateLimiter`）：实现简单、没有网络开销，但**限流阈值是"每台机器"的**，10 台机器各限 100，实际总放行 1000，达不到全局控制的效果。而且流量不均时，有的机器被打满、有的空闲。
>
> 用 Redis 的代价是**每次限流判断都多一次网络往返**，并且 Redis 成了限流链路的单点——Redis 挂了限流就失效。所以要么给限流加降级策略（Redis 不可用时直接放行，保可用性；或者直接拒绝，保安全性），要么用 Sentinel 这种把规则下发到本地、本地决策的方案。

---

### Q53. ⚠️ AOP 限流如果应用到同类内部调用的方法上，会生效吗？

**经典 AOP 陷阱题。**

> **不会生效。** Spring AOP 是基于**动态代理**的，外部调用走的是代理对象，代理才能插入切面逻辑；而类内部方法直接 `this.method()` 调用，走的是原始对象，绕过了代理。
>
> 解决办法有三种：
> **一是把方法拆到另一个 Bean 里**，通过注入调用。最干净，推荐。
> **二是注入自己**（`@Autowired private XxxService self;`），用 `self.method()` 调用。要注意循环依赖问题。
> **三是用 `AopContext.currentProxy()`**，需要开启 `@EnableAspectJAutoProxy(exposeProxy = true)`。
>
> 另外一个相关的坑：**`private` 和 `final` 方法上的注解也不生效**，因为 CGLIB 没法覆写。限流注解一定要加在 `public` 方法上。

---

### Q54. 限流返回 429 状态码，为什么用这个？

> 429 是 HTTP 标准里的 "**Too Many Requests**"，语义就是"请求过于频繁"。用标准状态码的好处是**前端和网关能统一识别处理**，不用每个接口自己约定。
>
> 更重要的是，**在网关层和监控里能直接按状态码统计限流次数**。如果我自己定义个 500 或者业务码，监控系统就看不出来这是限流导致的还是真的系统故障，排查时会误导人。
>
> 响应里我还应该带上 `Retry-After` 头告诉客户端什么时候可以重试，这是 429 的标准配套，我目前没加。

---

### Q55. 除了限流，你还做了哪些安全防范？

> 简历里写的"系统安全防范"主要是限流这一块，具体有：
> **一是随机码**，抬高脚本构造请求的门槛；
> **二是滑动窗口限流**，按用户、IP、接口三个维度限制频率；
> **三是越权校验**，查订单结果时校验 `userId` 归属，防止水平越权；
> **四是取真实 IP**，用 `X-Forwarded-For` 的第一个值，避免反代后所有请求看起来来自同一个 IP 导致限流失效。
>
> 还应该做但没做的：**登录态的防重放**（加时间戳和 nonce）、**参数校验**（防止 SQL 注入和 XSS）、**敏感操作的二次验证**。

### Q56. 如果攻击者用大量不同 IP 来刷，你的 IP 维度限流还有用吗？

> 作用有限。**IP 限流的前提是攻击成本**——攻击者要么用代理池，要么用肉鸡，成本越高越好。
>
> 应对上要分层：
> **一是换个维度**，比如按**用户 ID** 限流（需要登录，攻击者得注册大量账号，成本更高）；或者按**设备指纹**，但移动端采集和隐私有争议。
> **二是全局兜底**，设置一个**总的接口 QPS 上限**，不管多少 IP，总量超了就限。这样至少能保住系统不被打垮，牺牲的是正常用户。
> **三是上专业的风控/WAF**，做行为分析——正常用户和脚本的请求间隔、参数分布、访问路径都有明显区别。这是专职团队做的事，不是业务开发能覆盖的。
>
> 我的定位是：**应用层限流是低成本的第一道防线，能挡住大部分无脑脚本；真正的 DDoS 要靠基础设施层解决。**

### Q57. 介绍一下这个心理监控智能体项目。

> 这是一个"**轻量级智能聊天 + 全链路心理状态监测**"的一体化平台，给学校心理咨询场景用的。
>
> 核心解决两个问题：一是学生可以通过对话的方式做心理倾诉，二是老师能及时发现高风险学生。
>
> 技术上分三块：
> **对话侧**，用 Spring AI 对接 Ollama 本地部署的大模型，通过 Flux 构建流式会话接口，用户能像用 ChatGPT 一样看到逐字输出。
> **知识侧**，用 RAG 做知识增强——管理员上传心理咨询的知识文档，我把它们向量化存到 Chroma 向量数据库，用户提问时先检索相关知识再交给模型，让回答更专业、更贴合学校场景。
> **监测侧**，对对话内容做心理状态识别，识别到高风险自动触发预警。
>
> 另外用 MCP 协议集成外部服务，把监测数据自动归集、导出成 Excel，给老师做台账。

### Q58. Spring AI 和 LangChain4j 你都用过，为什么两个项目选了不同的框架？

**⚠️ 这题很能体现你的思考，因为你的两个项目恰好各用一个。**

> 主要是**项目启动的时间和场景不同**。
>
> **校园文创平台**用的 LangChain4j，当时主要是为了 **Function Calling**——让 AI 能根据用户需求自动调用后端接口查实时库存。LangChain4j 的 `@Tool` 注解对工具调用的封装比较顺手，而且它和 Spring Boot 的集成方式比较轻。

> **心理监控**用的 Spring AI，是因为这个项目更"**Spring 原生**"——用 Spring Security 做鉴权、用 Spring AI 的话整个技术栈统一在 Spring 生态里，依赖管理和自动配置更自然。而且 Spring AI 对流式响应的支持（`Flux<ChatResponse>`）和 WebFlux 结合得很好。
>
> 如果让我总结：**LangChain4j 的 AI 抽象层更厚，功能封装更多；Spring AI 更贴近 Spring 的使用习惯，和现有 Spring 项目的融合更顺。** 选哪个更多是看项目已经在用什么生态，而不是哪个绝对更好。

### Q59. Flux 是什么？流式响应是怎么实现的？

> `Flux` 是 **Reactor** 里的类型，代表一个**可以发出 0 到 N 个元素的异步序列**，是响应式编程的核心抽象。对应的 `Mono` 是 0 或 1 个元素。
>
> 流式响应的实现链路是：
> 大模型的返回本身是**逐 token 生成的**，Spring AI 会把这些 token 包装成 `Flux<ChatResponse>`，每一个 token 到达时 Flux 就发一个元素。
> Controller 返回这个 Flux 后，Spring 会把它写成 **SSE（Server-Sent Events）** 格式的响应——本质是一个 `Content-Type: text/event-stream` 的长连接，服务端持续往客户端推数据。
> 浏览器端用 `EventSource` 或者 `fetch` 的 stream 读取，就能实现"逐字打字机"的效果。
>
> 关键点是**整个链路必须是非阻塞的**。如果用传统的 Spring MVC，一个长连接会占住一个 Tomcat 线程；用 Spring AI 的流式接口要配合 **WebFlux**，用少量线程支撑大量并发连接。

### Q60. RAG 的完整流程讲一下。

> RAG 是"检索增强生成"，分**离线**和**在线**两条链路。
>
> **离线（知识库构建）**：
> 1. **文档加载**——管理员上传知识文档，解析成文本；
> 2. **分块（Chunking）**——把长文本切成小段，因为大模型的上下文窗口有限，而且检索粒度太粗会引入无关信息。分块策略很关键，要保留语义完整性，通常会设置重叠部分避免切断语义；
> 3. **向量化（Embedding）**——用 Embedding 模型把每个块转成一个高维向量；
> 4. **存储**——把向量和原文一起存进向量数据库（我用的是 Chroma）。
>
> **在线（问答）**：
> 1. 用户提问，同样用 Embedding 模型把问题转成向量；
> 2. 在向量库里做**相似度检索**，找出最相关的 Top K 个文本块；
> 3. 把这些文本块作为**上下文拼进 Prompt**，连同用户问题一起发给大模型；
> 4. 模型基于给定的上下文回答，而不是完全靠自己的参数记忆。
>
> 核心价值是**让模型的回答有依据、可溯源，并且能覆盖模型训练数据里没有的私有知识**。

### Q61. ⚠️ 简历写"准确率提升到 90%"，这个准确率是怎么评测的？

**必问，而且是最容易翻车的一题。**

> 说明评测方法，**关键要说清楚"准确率"是在什么数据集上、用什么口径算的**。
>
> 我的做法是：
> **第一步，构造评测集。** 从心理咨询的真实对话（脱敏后）里挑出样本，**由心理老师标注**每条对话对应的心理状态等级，作为"标准答案"。这是最关键的一步——**没有人工标注的评测集，任何准确率都是假的**。
> **第二步，划分数据集。** 分成训练集和**测试集**，微调只用训练集，评测只在测试集上做，避免"见过答案"导致的虚高。
> **第三步，定义口径。** 准确率 = 预测正确的样本数 / 总样本数。因为是多分类（不同风险等级），我还会看**混淆矩阵**，特别是**高风险的召回率**——漏掉一个高风险学生比误判一个正常学生严重得多。
> **第四步，做对比实验。** 用同一个测试集，分别跑微调前的基础模型和微调后的模型，得到的提升才是"LoRA 微调带来的效果"。
>
> 局限我也要说明：**样本量有限，而且标注本身带有主观性**，不同心理老师对同一段对话的判断可能不一致。所以这个 90% 应该理解为"**在我这个测试集上的表现**"，不等于真实场景的泛化能力。要更严谨，需要扩大样本量、引入多个标注者做一致性校验（比如 Kappa 系数）。

**⚠️ 如果你实际没做过这套流程，务必诚实**：可以说"我当时的评测做得比较粗糙，是拿一批对话手工对比的，现在回头看应该补一个规范的评测集"——**主动承认方法粗糙，比编造一个精密流程然后被追问细节答不上来安全得多**。

### Q62. LoRA 微调的原理是什么？为什么用它而不是全量微调？

> **LoRA（Low-Rank Adaptation，低秩适配）**的核心思想是：**冻结原模型的全部参数，只在旁边训练一对小的低秩矩阵**。
>
> 具体来说，假设原来某一层的权重矩阵是 `W`（比如 4096×4096，1600 万参数），LoRA 不去改它，而是另外学两个小矩阵 `A`（4096×r）和 `B`（r×4096），其中 `r` 是远小于 4096 的秩，比如 8 或 16。前向传播变成 `h = Wx + BAx`，训练时只更新 `A` 和 `B`。
>
> 这样可训练参数从 1600 万降到比如 6.5 万，**降低了两三个数量级**。
>
> **为什么用 LoRA：**
> **一是显存**。全量微调 7B 的模型，除了权重还要存优化器状态和梯度，显存需求是参数量的好几倍，消费级显卡根本跑不动。LoRA 只训极少参数，显存占用大幅下降。
> **二是速度**，参数量小，训练快。
> **三是可以多套适配器**，基础模型只存一份，不同任务用不同的 LoRA 权重，切换时加载对应的就行，部署成本低。
> **四是缓解灾难性遗忘**，因为原模型参数被冻结了。
>
> 代价是**效果通常略逊于全量微调**，但在数据量不大（我的场景就是）、任务比较聚焦的情况下，差距很小，性价比极高。

### Q63. 什么是 MCP？你用它做了什么？

> **MCP（Model Context Protocol，模型上下文协议）**是 Anthropic 提出的一个开放协议，目的是**标准化大模型和外部工具/数据源的连接方式**。
>
> 类比一下：**MCP 之于 AI 应用，就像 USB 之于外设**。在 MCP 之前，每个模型对接每个工具都要写一套定制代码；有了 MCP，工具方按协议实现一个 MCP Server，任何支持 MCP 的模型都能直接调用。
>
> 我在项目里的用法是：把"**记录监测数据**"和"**导出 Excel**"这两个能力做成 MCP 服务，让大模型在对话过程中可以主动调用——比如识别到某个学生持续处于焦虑状态，模型可以调用记录接口把这次评估结构化存下来，需要时再调用导出接口生成台账。
>
> 相比 Function Calling，MCP 的好处是**工具的定义和实现是解耦的、可复用的**，而且可以跨模型、跨应用使用。

### Q64. 对话上下文你是怎么维护的？无限增长怎么办？

> 上下文我存在 Redis 里，按会话 ID 组织，保留最近若干轮的对话。
>
> **无限增长确实是问题**，因为大模型的上下文窗口有硬限制（哪怕是 128K 也有上限），而且**token 越多成本越高、响应越慢**，还容易出现"中间遗忘"——上下文太长时模型对中间部分的注意力会下降。
>
> 处理策略有三层：
> **一是滑动窗口**，只保留最近 N 轮，最简单但会丢掉早期信息。
> **二是摘要压缩**，把超出窗口的早期对话让模型总结成一段摘要，作为"历史背景"拼在开头，保留关键信息。
> **三是关键信息提取**，把对话里确定的用户信息（比如"大二学生""最近在准备考研"）结构化抽出来单独存，每次对话作为固定上下文注入，比原始对话省 token 得多。
>
> 我的实现是第一层加第三层的简化版。如果要优化，会加上摘要压缩。

### Q65. 大模型的幻觉问题你怎么处理？

> 分几个层面：
> **一是靠 RAG 约束**。让模型基于检索到的知识回答，并在 Prompt 里明确要求"**如果知识库中没有相关信息，就直接说不确定，不要编造**"。这是最直接的手段。
> **二是降低检索的 Top K 和相似度阈值**，宁可少给也不要给不相关的，因为不相关的上下文反而会诱导模型编造。
> **三是引用溯源**，让模型在回答里标注信息来自哪个文档片段，老师和学生可以核对。这也让幻觉更容易被发现。
> **四是人工兜底**。这是心理场景，我定位得很清楚——**AI 的建议只作为参考，绝不能替代专业心理咨询师**。高风险识别触发的也是"通知老师介入"，而不是让 AI 直接给干预方案。
>
> 在做心理这种高风险场景时，**我认为最重要的不是消灭幻觉，而是设计好"幻觉发生时不会造成伤害"的流程**。

### Q66. 向量检索的相似度是怎么算的？

> 常用三种：
> **余弦相似度**——算两个向量夹角的余弦值，只关心方向不关心长度。**最常用**，因为文本向量的语义主要由方向表达。
> **点积**——受向量长度影响，如果向量都归一化了，点积等价于余弦相似度。
> **欧氏距离**——算直线距离，值越小越相似。
>
> 实际工程里主流向量库（包括 Chroma）默认用**余弦相似度**。
>
> 检索本身用的是 **ANN（近似最近邻）**算法而不是暴力遍历——因为向量可能有几百万条，暴力计算太慢。常用的有 HNSW（基于图的）和 IVF（基于聚类的），代价是**牺牲一点召回率换速度**。

### Q67. "动态路由 RAG"具体路由什么？

> 路由的是**"这个问题该去哪个知识库检索"**。
>
> 最简单的 RAG 是单库检索——所有知识混在一个向量库里，用户问什么都是全库相似度搜索。问题是**不同领域的内容会互相干扰**：用户问"考试焦虑怎么办"，如果库里还混着"危机干预流程""用药指导"的内容，检索出来的 Top K 可能被不相关的块占据。
>
> 动态路由的做法是：**先判断问题属于哪个领域，再只在该领域的子库检索**。
>
> 实现方式有几种：
> 一是**用大模型做意图分类**，先问模型"这个问题属于哪一类"，拿到类别再去对应库检索；
> 二是**用规则或关键词**做粗分类；
> 三是**每个库各自检索，再用重排序（Rerank）模型统一排序**。
>
> 我用的是第一种加第三种结合——先按大类缩小范围，再用重排序模型精选。
>
> 好处是**检索精度明显提升**，代价是**多了一次模型调用，延迟增加**，而且分类错了会直接检索不到正确内容，所以分类这一步的兜底要设计好（分类不确定时就全库检索）。

### Q70. 定时任务生成工单，幂等是怎么做的？

> 用 **Redis Key 做幂等锁**。
>
> 每次生成前，先根据"任务 + 时间周期"拼一个唯一的 key，用 `SETNX` 尝试写入。写成功才执行生成，写失败说明这个周期的工单已经被生成过了，直接跳过。
>
> **为什么 key 要带时间周期**：同一个任务每分钟都会跑，但工单是按天/按周生成的。key 里带上周期标识（比如 `daily:20260921`），保证"同一天只生成一次"，而不是"这个任务只跑一次"。
>
> **为什么要设 TTL**：不设过期的话 key 会永久累积。TTL 设成略大于周期长度，比如按天生成的设 25 小时，保证覆盖到下一次执行，同时自动清理。
>
> 这里有个关键点：**幂等和事务要配合**。我在 `SETNX` 成功之后才开启事务，事务失败的话要把 Redis 的 key 删掉（或者在业务异常时主动释放），否则会出现"锁住了但业务失败了，这个周期永远不会重试"的情况。

---

### Q71. 事务和 Redis 幂等锁，会不会出现"锁释放了但事务还没提交"的问题？

**⚠️ 这是个很尖锐的追问。**

> 会有这个问题。如果锁的 TTL 到了自动过期，而事务还在执行，另一个线程就能拿到锁进来重复执行。
>
> 应对方式：
> **一是锁的 TTL 要大于事务的最大执行时间**，并且订单量大的话可以加**看门狗续期**（Redisson 的 `tryLock` 带 leaseTime 参数就有这个能力）。
> **二是数据库层加唯一约束兜底**——比如"任务ID + 执行周期"建唯一索引，即使 Redis 锁失效导致重复执行，第二次插入也会被数据库挡住。**这是最关键的一层，因为分布式锁本质上不可能 100% 可靠**。
> **三是释放锁时校验持有者**，删 key 前先确认是自己的（用 Lua 比较 value），避免删掉别人的锁。
>
> 我实习时用的是第一种，靠 TTL 设置得足够宽。如果有机会重做，我会把**数据库唯一约束**作为最终防线补上——这是原则：**分布式锁是用来减少冲突的，不是用来保证正确性的**。

### Q72. 模板填充引擎是怎么实现的？为什么说"模板调整零发版"？

> 用的是 **Apache POI** 操作 Word 和 Excel 文件。
>
> 核心思路是**把模板从代码里挪出来，变成外置文件**：
> 模板文件放在一个配置化的目录下（或者打成 jar 外的路径），里面用占位符标注需要填充的位置，比如 `${工单编号}`、`${处理人}`。代码只负责读取模板、把占位符替换成真实数据、输出文件。
>
> **"零发版"的意义**：以前模板如果硬编码在 Java 代码里，运营想调整一下表格的标题、加一列，都要走需求 → 开发 → 改代码 → 测试 → 发版流程，几天就过去了。改成外置模板后，运营直接改模板文件替换上去就行，**开发和运维成本降到零**。
>
> 难点在**嵌套表格和动态行**：简单的占位符替换用一个 Map 就能做，但表格里需要"根据数据条数动态生成多行"，POI 里要处理行的复制和样式的保留。我的做法是**识别模板里的标记行**（比如某一行含有特殊的 `{{#each}}` 标记），以它为样板复制 N 行再逐行填充。

### Q73. 电子签名的"图片优先、文本兜底"是什么？

> 电子签名有两种形态：用户上传的**手写签名图片**，或者是系统生成的**文本签名**。
>
> "图片优先"是说：如果用户上传了签名图片，就优先用图片嵌入到文档里，效果最接近真实签名。
> "文本兜底"是说：如果用户没上传图片，或者图片文件有问题，就退化成用文本形式（比如用户名 + 时间戳）作为签名，**保证流程不会因为一个签名文件缺失而卡死**。
>
> 这是一个典型的**降级设计**——核心业务（工单归档）不能因为非关键的附件问题而中断。

### Q74. "文件魔数校验"是什么？为什么不看文件后缀？

> **魔数（Magic Number）是文件头部的固定字节**，用来标识文件真实类型。比如 JPEG 的前两个字节是 `FF D8`，PNG 是 `89 50 4E 47`，PDF 是 `%PDF`。
>
> 为什么不看后缀：**后缀只是个文件名，用户和攻击者可以随意改**。把一个 `.jsp` 文件改名成 `.jpg` 上传，如果服务端只看后缀就放行，后面这个文件被当成 JSP 解析执行，就是**任意代码执行漏洞**。这是文件上传功能最经典的安全问题。
>
> 所以正确的做法是**读取文件头的前几个字节，比对魔数，确认真实类型**。我在代码里对签名图片做了这个校验。
>
> 补充一点：光校验魔数也不够，还有**图片二次渲染**（把图片解码再用服务端代码重新编码，能洗掉图片里藏的恶意 payload）、**限制文件大小**、**文件名随机化并剥离路径**（防目录穿越）这些措施，构成完整的上传安全防线。

### Q75. "将文件读取收口至文件服务统一接口"，为什么要这么做？

> 这是**解耦业务和存储**。
>
> 原来的问题是：工单服务、导出服务、签名服务各自都要读文件，读的方式可能不一样（有的读本地磁盘，有的读 OSS，有的读 NAS）。哪天存储要迁移，要改好几个地方，容易漏。
>
> 收口之后，**所有文件读写都走文件服务的统一接口**，业务方不关心文件存在哪、怎么取。好处：
> **一是存储介质可以随时换**，比如从本地磁盘换成 MinIO 或 OSS，只改文件服务一处；
> **二是权限和校验统一**，魔数校验、大小限制、病毒扫描这些在文件服务里做一次，所有调用方都受益；
> **三是便于统一治理**，比如加缓存、加限流、加审计日志。

### Q76. 这个系统用了微服务，服务之间怎么通信？遇到过什么问题？

> 同步调用主要走 **OpenFeign**，通过网关和注册中心发现服务；异步的通信用消息队列。
>
> 踩过的典型问题：
> **一是服务雪崩**，A 调 B、B 调 C，C 慢了会把 B 的线程池占满，再传染到 A。解决办法是 **Sentinel 熔断降级**，给 Feign 调用配超时和熔断规则，C 挂了就返回兜底数据。
> **二是分布式事务**，比如生成工单要同时写工单库和任务库，跨服务没法用一个本地事务。我们的场景对一致性要求不是强一致，用了**本地消息表 + 定时重试**做到最终一致。
> **三是链路排查困难**，请求跨了好几个服务，出问题不知道是哪一环。用了 **SkyWalking** 做链路追踪，每个请求有统一的 traceId。

### Q77. PostgreSQL 和 MySQL 你都用过，有什么区别？

> 主要差异：
> **一是事务隔离级别默认不同**。PostgreSQL 默认是**读已提交**，MySQL 的 InnoDB 默认是**可重复读**。这个差异会直接影响业务表现——比如同一个事务里读两次，MySQL 默认拿到相同结果，PG 可能拿到不同的。
> **二是索引结构**。MySQL 主键索引是**聚簇索引**，数据行存在叶子节点上，二级索引存的是主键值，所以二级索引查询要"回表"。PG 用的是 **Heap 表 + 独立索引**，索引里存的是行物理位置（ctid）。
> **三是功能**。PG 的功能更强，支持更丰富的数据类型（数组、JSONB、几何类型）、更好的窗口函数、还有丰富的扩展。MySQL 更简单、生态更成熟、运维人才更多。
> **四是性能特点**。MySQL 在简单查询和高并发读上表现好，PG 在复杂查询、分析型场景更强。
>
> 选型上：**互联网高频简单读写多选 MySQL；业务复杂、数据类型丰富、需要强一致性保证的选 PostgreSQL**。实习项目用 PG，是因为工单系统有大量复杂查询和 JSON 字段。

**⚠️ 如果你 PG 的实际使用不深，答完这题可以补一句**："我在实习里主要是用 PG 写业务 SQL，底层的差异是后来自己补的，没有在生产环境做过 PG 的调优。"——诚实划定边界。

### Q78. 数据迁移你做了什么？

> 负责滨海湾新区基础设施数据的迁移工作。
>
> 主要流程是：**存量数据梳理 → 字段映射 → 数据清洗 → 分批导入 → 一致性校验**。
>
> 关键点：
> **一是分批迁移**，不能一次性全量导入，量大容易超时和锁表。用分页或者按 ID 区间分批，每批之间留间隔，避开业务高峰期。
> **二是要可重入**，迁移脚本必须能重复执行——因为中途失败必然要重跑。做法是记录迁移进度（比如维护一张迁移日志表，记录已完成的批次），重跑时跳过已完成的。
> **三是校验**，迁移前后对比记录数、关键字段的汇总值（比如金额总和），确保没有丢数据和错数据。
> **四是保留回滚能力**，迁移前备份，出问题能回退。

## 第七轮：Java 基础与并发

> 这轮是通用八股，几乎所有公司都会问。答案要**简短、准确、有画面感**，不要背长篇大论。

### Q80. `HashMap` 的底层结构？为什么线程不安全？

> JDK 8 之后是 **数组 + 链表 + 红黑树**。数组是哈希桶，冲突的元素挂成链表；当**链表长度达到 8 且数组长度达到 64** 时，链表转成红黑树，把查找从 O(n) 降到 O(logN)。
>
> `put` 的流程：算 key 的 hash → 定位桶 → 桶空就放，不空就比 hash 和 equals，相同就覆盖，不同就挂到链表/树后面。**扩容**是当元素数超过 `容量 × 0.75`（负载因子）时，容量翻倍并重新分配元素。
>
> **线程不安全的表现**：
> **一是数据覆盖**，两个线程同时 put 到同一个空桶，都判断为空，后写的覆盖先写的，丢数据。
> **二是 JDK 7 的链表成环**，多线程同时扩容时头插法可能让链表首尾相连，之后 `get` 一个不存在的 key 会死循环把 CPU 打满。JDK 8 改成尾插法后这个问题没了，但**仍然不安全**（还是会有数据覆盖）。
>
> 并发场景用 `ConcurrentHashMap`。

### Q81. `ConcurrentHashMap` 怎么保证线程安全？和 `Hashtable` 有什么区别？

> **Hashtable** 是给整个表加一把 `synchronized` 锁，任何操作都串行，并发度极低，基本没人用了。
>
> **ConcurrentHashMap** 的演进：
> **JDK 7** 用**分段锁**，把表分成 16 个 Segment，每段一把锁，不同段可以并行。并发度是 16。
> **JDK 8** 抛弃分段锁，改成 **CAS + synchronized 锁单个桶**。写入时如果桶为空用 CAS 直接放，不空就 `synchronized` 锁住这个桶的头节点。锁的粒度细到单个桶，并发度等于桶的数量，理论上更高。
>
> 另外几个关键点：**读操作完全不加锁**（value 用 `volatile` 修饰保证可见性），`size()` 用 `baseCount + CounterCell[]` 分散计数避免热点竞争。

### Q82. `volatile` 的作用是什么？能保证原子性吗？

> 两个作用：**保证可见性**和**禁止指令重排序**。
>
> **可见性**：一个线程改了 volatile 变量，其他线程立刻能看到。底层是写入后会插入内存屏障，把其他 CPU 核心里这个变量的缓存副本失效掉，强制重新从主存读。
> **禁止重排序**：防止编译器和 CPU 为了优化把指令顺序调整，导致其他线程看到"半成品"状态。
>
> **不能保证原子性**。典型的 `i++` 问题：`i++` 是"读 - 加 - 写"三步，两个线程可能都读到 1，都加 1 写回 2，实际应该是 3。volatile 拦不住这个。
>
> 这个特性正是 **DCL 单例要加 volatile** 的原因——`instance = new Singleton()` 分三步（分配内存、初始化对象、把引用指向内存），2 和 3 可能重排，导致另一个线程拿到"引用非空但对象还没初始化"的对象。

### Q83. `synchronized` 和 `ReentrantLock` 的区别？

| 维度 | synchronized | ReentrantLock |
|---|---|---|
| 实现层面 | JVM 关键字，monitor 指令 | JDK 层面，基于 AQS |
| 锁的释放 | 自动（异常也释放） | **必须手动 unlock，要放 finally** |
| 可中断 | 不支持 | 支持 `lockInterruptibly` |
| 超时 | 不支持 | 支持 `tryLock(timeout)` |
| 公平锁 | 只能非公平 | 可选公平/非公平 |
| 条件变量 | 一个 wait/notify | 可创建多个 Condition |

> 一句话总结：**简单场景用 synchronized，需要超时、可中断、多条件队列这些高级能力时才用 ReentrantLock**。
>
> 补充一个点：**synchronized 在 JDK 6 之后做了大量优化**（偏向锁、轻量级锁、锁消除、锁粗化），性能已经和 ReentrantLock 差不多了，不要再用"性能差"当理由拒绝它。
>
> 我的缓存重建用的是 Redisson 的 RLock，那是**分布式锁**，解决的是跨进程的问题，和这两个本地锁不是一个层面。

### Q84. 线程池的核心参数有哪些？执行流程是怎样的？

> 七个参数：**核心线程数、最大线程数、空闲存活时间、时间单位、工作队列、线程工厂、拒绝策略**。
>
> 执行流程：
> 1. 线程数 < 核心线程数 → **新建核心线程**执行；
> 2. 核心线程满了 → **任务入队**；
> 3. 队列满了且线程数 < 最大线程数 → **新建非核心线程**；
> 4. 队列满且线程数 = 最大线程数 → **执行拒绝策略**。
>
> 关键理解：**先入队，队列满了才扩容线程**。这个顺序很多人搞反。原因是设计者认为"用队列缓冲比频繁创建线程更划算"。
>
> 非核心线程空闲超过存活时间会被回收，核心线程默认不回收（可以设 `allowCoreThreadTimeOut` 改变）。

### Q85. 线程池参数怎么设置？为什么阿里规范禁止用 `Executors`？

> **禁止 `Executors` 的原因**是它创建的线程池有两个极端隐患：
> `newFixedThreadPool` 和 `newSingleThreadExecutor` 用的是 **`LinkedBlockingQueue`，默认容量是 `Integer.MAX_VALUE`**——相当于无界队列。任务堆积时不会触发拒绝策略，而是一直往队列里塞，最终 **OOM**。
> `newCachedThreadPool` 的**最大线程数是 `Integer.MAX_VALUE`**——任务多了会无限制创建线程，最终**耗尽系统资源**（每个线程默认 1MB 栈）。
>
> 所以规范要求**手动 `new ThreadPoolExecutor`**，明确指定有界队列和拒绝策略。
>
> **参数怎么定**，是按任务类型分的：
> **CPU 密集型**（计算为主，比如加密、序列化）：线程数设为 **CPU 核数 + 1**，多了反而增加上下文切换开销。
> **IO 密集型**（等 DB、等 RPC）：线程数设为 **CPU 核数 × 2**，或者按公式 `核数 × (1 + 平均等待时间 / 平均计算时间)` 估算。
>
> 我 `CacheClient` 里的重建线程池是**低频 IO 任务**，核心 2 / 最大 4，队列 100 缓冲突发，用的是 `CallerRunsPolicy`（宁可降级成同步也不丢任务）。这个参数是拍脑袋定的合理值，不是精确计算——**真实场景应该根据监控数据（队列长度、拒绝次数）动态调整**。

### Q86. `ThreadLocal` 的原理？会有什么问题？

> 原理：每个 `Thread` 对象内部有一个 `ThreadLocalMap`，key 是 `ThreadLocal` 对象的**弱引用**，value 是存的值。所以数据是**按线程隔离**的，不同线程访问同一个 `ThreadLocal` 拿到的是各自的值。
>
> **内存泄漏问题**：`ThreadLocalMap` 的 key 是弱引用，value 是**强引用**。如果 `ThreadLocal` 对象被回收了（key 变成 null），但线程还活着（线程池里的线程是复用的，生命周期很长），这个 entry 的 value 就永远无法被访问但也无法被回收。
>
> **解决办法**：**用完必须 `remove()`**，而且要放在 `finally` 里。
>
> 我项目里 `UserHolder` 就是基于 `ThreadLocal` 存当前登录用户 ID 的。拦截器里 `set`，请求结束后必须 `remove`——**因为我们用的是 Tomcat 线程池，线程会复用，不清理的话下一个请求可能读到上一个用户的 ID**，这是严重的安全问题。

### Q87. 谈谈你对 JMM（Java 内存模型）的理解。

> JMM 是**一套规范**，定义了多线程环境下共享变量的可见性、有序性和原子性规则。核心是**抽象出主内存和工作内存**：每个线程有自己的工作内存（对应 CPU 缓存和寄存器），共享变量存在主内存，线程操作变量要先拷贝到工作内存。
>
> 三大特性：
> **原子性**：基本类型的读写是原子的，但复合操作（`i++`）不是，要靠 `synchronized` 或 `Atomic` 类。
> **可见性**：一个线程的修改其他线程能否立即看到，靠 `volatile`、`synchronized`、`final` 保证。
> **有序性**：`happens-before` 规则保证，比如"程序顺序规则""监视器锁规则""volatile 变量规则"。
>
> **happens-before 是理解 JMM 的关键**：如果 A happens-before B，那 A 的结果对 B 可见，且 A 的执行顺序在 B 之前。它不是"时间上的先后"，而是**可见性和顺序性的保证**。

### Q88. JVM 内存区域有哪些？

> 按线程私有/共享分：
> **线程私有**：
> - **程序计数器**：记录当前线程执行的字节码行号，唯一不会 OOM 的区域；
> - **虚拟机栈**：每个方法调用创建一个栈帧，存局部变量表、操作数栈等。栈太深会 `StackOverflowError`；
> - **本地方法栈**：给 native 方法用。
>
> **线程共享**：
> - **堆**：对象实例都在这里，GC 的主战场，分新生代（Eden + 两个 Survivor）和老年代；
> - **方法区 / 元空间**：存类元信息、常量、静态变量。JDK 8 之后从永久代改成**元空间，用本地内存**，所以不再受 `-XX:MaxPermSize` 限制。
>
> **直接内存**：NIO 用的 `DirectByteBuffer` 分配在堆外，不受堆大小限制但受物理内存限制。

### Q89. 怎么判断一个对象该被回收？GC Roots 有哪些？

> 主流是**可达性分析**：从一组叫 `GC Roots` 的对象出发，能到达的对象是存活的，到达不了的就该回收。
>
> 为什么不用引用计数法：**解决不了循环引用**——A 引用 B、B 引用 A，两者都不再被使用但计数都不为 0。
>
> **GC Roots 包括**：虚拟机栈中局部变量表引用的对象、方法区中静态变量引用的对象、方法区常量引用的对象、本地方法栈中 native 方法引用的对象。
>
> 补充一点：对象被判定不可达后不是立刻回收，还要看 `finalize()` 方法——如果类覆写了且没执行过，会先放进 F-Queue 里执行一次，这也是个"自救"机会。但 `finalize` 已经不推荐使用了。

### Q90. 常见的垃圾回收器有哪些？了解 G1 吗？

> 分几代：
> **新生代**：`Serial`（单线程，客户端模式）、`ParNew`（多线程版 Serial）、`Parallel Scavenge`（吞吐量优先，JDK 8 默认新生代）。
> **老年代**：`Serial Old`、`Parallel Old`、`CMS`（并发标记清除，追求低停顿，但会产生内存碎片和并发失败）。
> **整堆**：**`G1`**（JDK 9 之后的默认）、`ZGC`、`Shenandoah`。
>
> **G1 的核心特点**是**把堆拆成很多个大小相等的 Region**（不再物理分代，逻辑上分），然后**根据每个 Region 的回收收益排序，优先回收收益最高的**——"Garbage First"的名字就是这么来的。用户可以设定预期的停顿时间（`-XX:MaxGCPauseMillis`），G1 会努力在这个时间内完成回收。
>
> 相比 CMS 的优势：**可预测的停顿时间、不会产生内存碎片**（Region 之间可以做复制）、更适合大堆（6GB 以上）。
>
> 如果问到我用哪个：我项目里是默认配置，没有做过 GC 调优——**小项目没必要，调优是在有明确性能问题、有监控数据的情况下才做的事**。

### Q91. 线上 CPU 飙升到 100%，你怎么排查？

**⚠️ 场景题，考察实操经验，几乎必问。**

> 按这个步骤来：
> **第一步，定位是哪个进程。** `top` 找到 CPU 最高的 Java 进程 PID。
> **第二步，定位是哪个线程。** `top -Hp <pid>` 找出 CPU 最高的线程，把它的十进制 TID 转成十六进制：`printf "%x\n" <tid>`。
> **第三步，看线程栈。** `jstack <pid> > stack.log`，在文件里搜那个十六进制 TID，就能看到这个线程在干什么。
>
> **常见原因和对策**：
> - **死循环 / 大量计算**：栈里会看到某个业务方法的持续调用；
> - **GC 频繁**：用 `jstat -gcutil <pid> 1000` 看 GC 次数和耗时，如果 Full GC 频繁且回收效果差，说明内存泄漏或堆太小，配合 `jmap -dump` 导出堆快照用 MAT 分析；
> - **线程上下文切换过多**：`vmstat` 看 `cs` 列，可能是锁竞争激烈或者线程数过多；
> - **频繁的日志输出**：这个最容易被忽略，同步日志在高并发下非常耗 CPU。
>
> 我自己的项目里没遇到过线上 CPU 问题（因为没上生产），但这套流程我在本地用 `jstack` 排查过一次线程池的问题——**异步重建线程池的异常没有 catch，导致任务静默失败**，就是靠看线程栈发现的。

---

### Q92. `ArrayList` 和 `LinkedList` 怎么选？

> **ArrayList 基于数组**，支持随机访问（O(1)），尾部插入快，中间插入/删除要移动元素（O(n)），扩容时复制到新数组（1.5 倍）。
> **LinkedList 基于双向链表**，随机访问要遍历（O(n)），但已知节点位置时插入删除是 O(1)，额外内存开销大（每个节点存前后指针）。
>
> 实践中的结论有点反直觉：**绝大多数场景都用 `ArrayList`**。因为 CPU 缓存友好性——数组是连续内存，遍历时命中缓存；链表节点分散在堆里，每次访问都可能缓存未命中。所以即使是频繁中间插入的场景，ArrayList 在小数据量下也常常更快。
>
> 真正需要 O(1) 头尾操作时，用 `ArrayDeque` 而不是 `LinkedList`。

---

### Q93. `final`、`finally`、`finalize` 的区别？

> - **`final`** 是修饰符：修饰类不能被继承，修饰方法不能被重写，修饰变量不能被重新赋值（引用不可变，但对象内容可变）。
> - **`finally`** 是异常处理块，不管有没有异常都会执行，**常用于释放资源**（关流、关连接、`ThreadLocal.remove()`）。
> - **`finalize`** 是 `Object` 的方法，对象被回收前调用。**已经废弃**，因为执行时机不确定、可能让对象"复活"、拖慢 GC。
>
> 一个易错点：**`finally` 里如果写了 `return`，会覆盖掉 try 里的返回值**，还会吞掉异常，是绝对的编码禁忌。

## 第八轮：MySQL

### Q94. 索引的底层为什么用 B+ 树？B 树不行吗？

> 三个原因：
> **一是 B+ 树矮胖，磁盘 IO 次数少。** 非叶子节点不存数据只存索引，所以一个节点能放更多 key，树高更低。三层 B+ 树就能存两千万行左右，查一次最多 3 次磁盘 IO。
> **二是 B+ 树叶子节点是链表，范围查询快。** `WHERE id BETWEEN 10 AND 100` 只需要定位到 10 然后顺着链表扫。B 树要做中序遍历，回溯麻烦。
> **三是查询性能稳定。** B+ 树所有数据都在叶子节点，每次查询都要走到叶子，IO 次数一致。B 树的数据可能在非叶子节点就命中，性能不稳定。
>
> 对比其他结构：**哈希索引**虽然 O(1)，但**不支持范围查询和排序**；**二叉树/红黑树**树高太高，磁盘 IO 次数多。

### Q95. 什么是回表？什么是覆盖索引？什么是索引下推？

> **回表**：InnoDB 的二级索引（非主键索引）叶子节点存的是**主键值**。所以通过二级索引查到主键后，还要拿主键去主键索引（聚簇索引）里再查一次完整数据行，这次额外的查询就叫回表。
>
> **覆盖索引**：如果一个查询需要的所有字段都能从索引里拿到，**就不用回表**。比如 `SELECT id, name FROM user WHERE name = 'x'`，如果建了 `(name, id)` 索引（其实二级索引天然包含主键），就只查索引就够。所以**避免 `SELECT *` 是有意义的**——减少回表，也可能用上覆盖索引。
>
> **索引下推（ICP，MySQL 5.6+）**：原本是"用索引字段过滤出主键 → 回表 → 再过滤其他条件"。下推是指**把索引里能判断的条件下推到存储引擎层**，在回表之前就用索引里的字段过滤掉不满足的行，减少回表次数。
> 比如 `WHERE name LIKE '张%' AND age = 20`，建了 `(name, age)` 索引，在 MySQL 5.5 时只能用 name 过滤，回表后再判 age；5.6 之后可以在索引里直接判 age，不符合的就不回表了。

### Q96. 什么情况会导致索引失效？

**高频必考，按"最容易被追问"排序：**

> 1. **对索引列做运算或函数**，比如 `WHERE YEAR(create_time) = 2026`、`WHERE id + 1 = 5`。改成范围查询 `create_time BETWEEN ... AND ...`。
> 2. **隐式类型转换**，比如 `phone` 是 varchar 但写 `WHERE phone = 13800000000`，MySQL 会把列转成数字，等于对列做了函数。**字符串字段的条件一定要加引号。**
> 3. **`LIKE` 以 `%` 开头**，`LIKE '%张'` 无法用索引（`LIKE '张%'` 可以）。
> 4. **不满足最左前缀原则**。联合索引 `(a, b, c)`，查询 `WHERE b = 1` 用不上；`WHERE a = 1 AND c = 2` 只能用到 a。
> 5. **`OR` 连接的条件不是全都有索引**，其中一个没索引就全表扫描。
> 6. **`!=`、`NOT IN`、`IS NOT NULL`** 这类负向条件，优化器判断全表扫描更划算时会放弃索引。
> 7. **优化器认为全表扫描更快**。比如表很小，或者要返回的数据占了表的大部分（通常超过 20-30%），走索引反而更慢。

### Q97. 什么是聚簇索引？主键为什么建议用自增 ID？

> **聚簇索引**是指**索引和数据存在一起**。InnoDB 的主键索引就是聚簇索引，叶子节点直接存完整的数据行。所以**一张表只能有一个聚簇索引**。
> 非主键索引（二级索引）的叶子节点存的是主键值，需要回表。
>
> **为什么用自增 ID**：
> **一是插入快**。自增 ID 保证新数据总是追加到 B+ 树的最右边，**不会引起页分裂**。如果用 UUID 这种随机值，新数据可能插到中间的任意位置，导致页分裂、数据移动、性能急剧下降，还会产生碎片。
> **二是主键会被二级索引引用**。主键越小，所有二级索引的叶子节点就越小，整个索引占的空间就越少，一次 IO 能读更多索引项。
>
> **为什么不用业务字段做主键**：业务字段可能修改（主键修改要级联改所有二级索引，代价极大），而且可能比较长（比如身份证号、手机号）。

### Q98. 事务的四大特性？隔离级别有哪些？分别解决什么问题？

> **ACID**：原子性（要么全成功要么全失败，靠 undo log）、一致性（约束不破坏）、隔离性（并发事务互不干扰，靠锁和 MVCC）、持久性（提交后不丢，靠 redo log）。
>
> **四个隔离级别**：

| 级别 | 脏读 | 不可重复读 | 幻读 |
|---|---|---|---|
| 读未提交 | ✗ | ✗ | ✗ |
| 读已提交 | ✓ | ✗ | ✗ |
| **可重复读**（MySQL 默认）| ✓ | ✓ | ✓（InnoDB 靠间隙锁基本解决）|
| 串行化 | ✓ | ✓ | ✓ |

> **现象解释**：
> **脏读**：读到了别的**未提交**事务的数据，对方回滚了就错了。
> **不可重复读**：同一个事务里两次读同一行，结果不同，因为别人**修改并提交**了。
> **幻读**：同一个事务里两次执行同一个范围查询，**行数变多了**，因为别人**插入并提交**了。
>
> **关键补充**：InnoDB 在**可重复读**级别下，靠 **MVCC + 间隙锁**基本解决了幻读。MVCC 通过 ReadView 保证快照读的结果一致，间隙锁防止其他事务在区间内插入新行。

---

### Q99. MVCC 的原理是什么？

> MVCC 是**多版本并发控制**，核心是**读不加锁、读写不冲突**。
>
> 三个关键组件：
> **一是隐藏字段**：每行数据有两个隐藏列——`trx_id`（最后一次修改这行的事务 ID）和 `roll_pointer`（指向 undo log 里的上一个版本）。
> **二是 undo log 版本链**：每次修改都会把旧值写进 undo log，通过 `roll_pointer` 串成一条版本链，可以追溯到历史版本。
> **三是 ReadView**：事务快照读时生成，记录了此刻"**活跃事务 ID 列表**"和"**最小活跃事务 ID**"。
>
> **可见性判断规则**：拿到一行的 `trx_id`，和 ReadView 比对——
> - 如果 `trx_id` 小于最小活跃 ID，说明这个事务早就提交了，**可见**；
> - 如果大于等于最小活跃 ID 且在活跃列表里，说明还没提交，**不可见**，顺着版本链往上找；
> - 如果大于最大 ID，说明是后面才开启的事务，**不可见**。
>
> **RC 和 RR 的区别就在 ReadView 的生成时机**：**RC 是每次快照读都重新生成** ReadView（所以能看到别人新提交的数据）；**RR 只在第一次快照读时生成**，之后复用（所以整个事务看到的是同一个快照）。

### Q100. `undo log` 和 `redo log` 的区别？

> - **redo log（重做日志）**：保证**持久性**。InnoDB 特有的，物理日志，记录"在某个数据页上做了什么修改"。用 **WAL（Write-Ahead Logging）**机制——修改先写 redo log（顺序写、快），再异步刷数据页（随机写、慢）。**崩溃后可以用 redo log 恢复未落盘的数据。**
> - **undo log（回滚日志）**：保证**原子性**，同时支撑 MVCC。逻辑日志，记录"反向操作"（insert 记 delete，update 记反向 update）。**事务回滚就是执行 undo log 里的反向操作。**
>
> redo log 是**循环写**（固定大小，用两个指针标记写入位置和待刷盘位置），undo log 是**增删**（事务提交后不一定立刻删，可能还被 MVCC 用着）。
>
> 顺带说 **binlog**（Server 层，归档日志，用于主从复制和数据恢复），和 redo log 的区别是三者的经典面试题：redo 是 InnoDB 层的物理日志、循环写；binlog 是 Server 层的逻辑日志（记录 SQL 或行变更）、追加写。**两阶段提交**就是用来保证这两个日志一致的。

### Q101. 一条 SQL 执行很慢，你怎么排查？

**⚠️ 场景题，简历里写了"能够排查优化慢查询"，必问。**

> **第一步，先定位是哪条 SQL。** 开启**慢查询日志**（`slow_query_log`，设 `long_query_time`），或者用 `SHOW PROCESSLIST` 看当前正在执行的语句。
>
> **第二步，用 `EXPLAIN` 分析执行计划。** 重点看几列：
> - **`type`**：访问类型，从好到坏是 `system > const > eq_ref > ref > range > index > ALL`。**出现 `ALL` 就是全表扫描，必须优化。**
> - **`key`**：实际用了哪个索引，是 `NULL` 说明没走索引。
> - **`rows`**：预估扫描行数，越大越慢。
> - **`Extra`**：`Using filesort` 说明额外排序（可能要优化排序字段的索引）、`Using temporary` 说明用了临时表（常见于 GROUP BY）、`Using index` 是覆盖索引（好现象）。
>
> **第三步，针对性优化：**
> - **加索引**：给 WHERE、ORDER BY、JOIN 的字段建合适的索引，注意最左前缀和区分度（区分度低的字段做索引效果差，比如性别）；
> - **改写 SQL**：避免 `SELECT *`、避免在索引列上做运算、把子查询改成 JOIN、大偏移量的分页改成"游标分页"（`WHERE id > 上一页最后一个id LIMIT 10` 而不是 `LIMIT 100000, 10`）；
> - **减少回表**，用覆盖索引；
> - **表结构优化**：字段类型选小的、拆大字段到子表；
> - **终极方案**：读写分离、分库分表、加缓存。
>
> **第四步，验证。** 改完再 `EXPLAIN` 看一次，对比 `rows` 和实际耗时。
>
> 我在项目里遇到的实际例子：`listActive()` 接口在循环里逐个查商品，是典型的 **N+1 问题**，21 次查询改成 2 次批量查询。这不是慢查询日志发现的，是**看代码 review 出来的**——所以优化慢查询不只靠工具，写代码时就要有意识。

### Q102. 什么是死锁？MySQL 里怎么排查和避免？

> 死锁是**两个或多个事务互相持有对方需要的锁，都在等对方释放**，形成环路。
>
> **MySQL 的排查**：
> - `SHOW ENGINE INNODB STATUS`，看 `LATEST DETECTED DEADLOCK` 段落，里面有死锁涉及的两个事务、各自的 SQL、持有的锁和等待的锁；
> - `performance_schema.data_locks` 和 `data_lock_waits` 表可以看当前的锁等待情况。
>
> **InnoDB 的处理**：检测到死锁会**自动回滚其中一个代价较小的事务**（修改行数少的），让另一个继续，报错 `Deadlock found when trying to get lock`。
>
> **避免死锁**：
> 1. **按固定顺序访问资源**。比如两个事务都要更新 A 和 B，约定都按"A 再 B"的顺序，就不会交叉。
> 2. **缩短事务，尽快提交**。事务越长，持锁时间越长，冲突概率越大。
> 3. **给条件加索引**，避免**锁范围扩大**——没有索引时 `UPDATE` 会锁全表或者大量行，冲突面剧增。
> 4. **降低隔离级别**（RC 下间隙锁少）或者用乐观锁（版本号）代替悲观锁。
> 5. 必要时用 `SELECT ... FOR UPDATE` 显式加锁，但要设 `innodb_lock_wait_timeout` 超时，避免无限等待。

---

### Q103. 乐观锁和悲观锁的区别？你在项目里用了吗？

> **悲观锁**假设冲突一定会发生，所以在操作前先加锁。数据库里就是 `SELECT ... FOR UPDATE`、`LOCK IN SHARE MODE`，Java 里就是 `synchronized`。**适合写多读少、冲突激烈的场景**，但会降低并发度。
>
> **乐观锁**假设冲突很少发生，不加锁，而是在更新时校验"数据有没有被别人改过"。实现有两种：**版本号**（`UPDATE ... SET v = v+1 WHERE id = ? AND v = 旧版本号`）和 **CAS**（Java 的 `AtomicInteger`、`compareAndSwap`）。**适合读多写少，冲突少时性能远高于悲观锁**，但冲突多时会大量重试反而更慢。
>
> **我的项目里的应用**：秒杀扣库存本质上是**乐观锁思路**——Redis 的 Lua 脚本里先判断库存 > 0 再扣减，是靠单线程串行保证的原子性，没有加锁；`CacheClient` 里用的是 **Redisson 分布式锁**（悲观锁思路），但用了 `tryLock()` 不等待，**抢不到就放弃**——这是个混合策略：悲观锁保证同一时刻只有一个人重建，非阻塞获取保证不会堆积等待。

### Q104. 分库分表了解吗？什么时候需要做？

> **垂直拆分**：按业务拆库（用户库、订单库），按字段拆表（把大字段、低频字段拆到扩展表）。
> **水平拆分**：同一个表按规则拆成多张。常用规则有**范围分片**（按时间/ID 区间，好处是扩容方便、老数据归档简单，坏处是热点集中在新片）和**哈希分片**（`user_id % N`，数据均匀但扩容要重新分布）。
>
> **什么时候做**：单表数据量**超过 1000 万行**左右（不是绝对，取决于行大小和查询模式），或者单库的磁盘/连接数成为瓶颈时。
>
> **但我的观点是：分库分表是最后的手段**。因为代价很大——**跨库 JOIN 做不了、分布式事务变复杂、全局 ID 要重新设计、扩容要数据迁移、运维复杂度陡增**。
> 在分库分表之前，有一大堆更便宜的优化可以做：**加索引、优化 SQL、加缓存、读写分离（主从复制）、归档冷数据**。这些做完还不够，再考虑分库分表。
>
> 中间件方面了解 ShardingSphere 和 MyCat，但我没有在生产环境实际落地过——**这块是我的知识盲区，我是看书和文档了解的**。

## 第九轮：Redis

### Q105. Redis 为什么快？

> 四点：
> 1. **纯内存操作**，不涉及磁盘 IO（这是最主要的原因）。
> 2. **单线程处理命令**，避免了多线程的锁竞争和上下文切换。要注意 Redis 6.0 之后网络 IO 是多线程的，**命令执行仍然是单线程**。
> 3. **IO 多路复用**（epoll），一个线程能处理大量连接，不用为每个连接创建线程。
> 4. **高效的数据结构**，比如 SDS（简单动态字符串）、跳表、ziplist/listpack、intset，针对不同数据量做了内存和性能的优化。
>
> 补充一句：**单线程的前提是"每个命令都要快"**。所以 Redis 里绝对不能放慢命令——`KEYS *`、`FLUSHALL`、大 key 的 `DEL`、以及**我用的 Lua 脚本里如果有循环**，都会阻塞整个 Redis。这也是我 `seckill.lua` 里只做 O(1) 操作的原因。

---

### Q106. Redis 的持久化方式？RDB 和 AOF 怎么选？

> **RDB（快照）**：把某个时间点的全量数据写成二进制文件。
> 优点是**文件小、恢复快**；缺点是**可能丢数据**（两次快照之间的写入会丢），而且 `fork` 子进程做快照时，数据量大可能有短暂阻塞。
>
> **AOF（追加日志）**：记录每一条写命令，追加到文件。
> 优点是**丢数据少**（`appendfsync everysec` 最多丢 1 秒）；缺点是**文件大、恢复慢**（要重放所有命令）。
>
> **AOF 重写**：AOF 会越来越大，Redis 会 fork 子进程根据当前数据状态生成一份"最小命令集"来替换旧文件。
>
> **怎么选**：
> - **纯缓存场景**（数据丢了能从 DB 恢复）→ **不持久化或者只开 RDB**，比如我项目里的商品缓存就属于这类；
> - **数据不能丢**（比如当作数据库用）→ **AOF + `everysec`，或者 RDB + AOF 混合**（Redis 4.0 支持 `aof-use-rdb-preamble`，重写时用 RDB 格式打头）。
>
> 我项目里库存这种**绝对不能丢**的数据，原则上是应该开 AOF 的——但也要承认，**秒杀库存本身在 DB 里有最终账本**，Redis 只是预扣闸门，丢了可以靠预热任务重建。

### Q107. 缓存和数据库的双写一致性，你怎么保证？

> 这个问题我在项目里是这样答的（见 Q42）：
> **先更新 DB，再删除缓存**，删除失败用 **Kafka 重试 + TTL 兜底**，保证**最终一致性**，接受短暂的不一致。
>
> 要强调的是**"最终一致"和"强一致"是两个完全不同的目标**：
> - **强一致**意味着每次读都必须拿到最新值，那缓存就没意义了（每次都要和 DB 校验）。真需要强一致就不该用缓存。
> - **最终一致**是"过一段时间后一致"，这才是缓存的合理目标。
>
> 在做业务时我一直用一个判断标准：**问业务方"这个数据晚 1 秒生效，能不能接受"**。能接受就用缓存 + 最终一致；不能接受（比如库存、余额），就**不能让缓存成为唯一数据源**，要让 DB 的校验兜住底线——这也是我秒杀里"Redis 挡流量、DB 保正确"两层防线的思路。

---

### Q108. Redis 是单线程的，为什么还能支持高并发？

> 关键在于**"单线程"指的是命令执行**，不是整个 Redis。
>
> **并发能力来自 IO 多路复用**：一个线程用 epoll 监听成千上万个连接，哪个连接有数据就处理哪个，不需要为每个连接创建线程。所以能同时维持大量连接。
>
> **吞吐能力来自内存操作**：单线程处理内存操作，单机就能到 10 万 QPS 量级——因为内存访问是纳秒级，瓶颈根本不在 CPU 而在网络。
>
> **单线程反而有优势**：没有锁竞争、没有线程切换开销、没有并发安全问题（这也是我的 Lua 脚本能天然原子的原因）。
>
> **瓶颈在哪**：单个命令的执行时间。所以**大 key、复杂命令、耗时 Lua 脚本是 Redis 的杀手**。如果要突破单机极限，就是 **Redis Cluster 分片**，把 key 分散到多个节点，每个节点还是单线程，但整体是并行的。

### Q109. 分布式锁你用 Redis 怎么实现？有什么坑？

> **最基础的实现**：`SET key value NX PX 30000`——`NX` 保证只有一个人能设成功，`PX` 设置过期时间防止死锁，`value` 存一个唯一标识（比如 UUID）用于释放时校验。
>
> **必须 `value` 存唯一标识 + Lua 释放**：`DEL` 之前要先比对 value 是不是自己的，比对和删除必须是原子的（用 Lua）。否则会出现：A 的锁超时了，B 拿到锁，A 执行完把 B 的锁删了。
>
> **三个经典坑**：
> **一是锁过期但业务没执行完**，另一个线程拿到锁，出现并发。解法是**看门狗续期**——Redisson 的 `RLock` 默认就有，后台线程每 10 秒（`lockWatchdogTimeout` 的 1/3）续一次期。
> **二是主从切换丢锁**。主节点写入锁还没同步到从节点就宕机了，从节点升主后锁丢了，另一个客户端能拿到。解法是 **Redisson 的 RedLock**，向多个独立节点申请锁，多数成功才算成功。但 **RedLock 本身有争议**（Martin Kleppmann 质疑过它在时钟漂移和 GC 停顿下的安全性）。
> **三是锁的粒度**。锁太粗（比如锁整个商品表）会严重影响并发，锁太细又可能漏掉要保护的资源。
>
> **我项目里用的就是 Redisson 的 RLock**（不是 RedLock），因为我的场景是**缓存重建的防击穿**，即使极低概率出现两个线程同时重建，也就是多查一次 DB、写一次缓存，**不影响正确性**。我明确知道这里不需要 RedLock 那么强的保证——**技术选型要对齐风险等级，不要为了炫技上重武器**。

### Q110. 什么是大 key 和热 key？怎么发现和处理？

> **大 key**：单个 key 的 value 特别大，比如一个 Hash 有几十万字段、一个 String 有几百 MB。
> **危害**：读大 key 会阻塞 Redis（单线程），网络传输耗时，删除时 `DEL` 也会阻塞（要用 `UNLINK` 异步删），还可能导致集群数据倾斜。
> **发现**：`redis-cli --bigkeys` 扫描，或者用 RDB 分析工具。
> **处理**：**拆分**（大 Hash 按字段拆成多个小 Hash）、**压缩**、**只存必要字段**。
>
> **热 key**：某个 key 被极高频率访问。
> **危害**：单节点 CPU 打满（集群下即使分片也救不了单个 key）。
> **发现**：`redis-cli --hotkeys`（需要 LFU 策略）、或者客户端埋点统计、或者用 `MONITOR` 采样（但 MONITOR 本身有性能损耗）。
> **处理**：
> - **本地缓存**——我在商品详情用的 **Caffeine 就是这个作用**，把热 key 挡在 JVM 里，Redis 都不用访问；
> - **key 打散**——比如库存分片，把 `stock` 拆成 `stock:1` ~ `stock:10`；
> - **读写分离**——热 key 分散到多个从节点读。
>
> 我项目里 `seckill:stock:{id}` 就是典型的**超级热 key**，Q23 里详细讲了分片方案。

### Q111. Redis 的过期删除策略和内存淘汰策略？

> **过期删除**用**惰性删除 + 定期删除**两种结合：
> **惰性删除**：访问 key 时才检查是否过期，过期就删。省 CPU，但过期没被访问的 key 会一直占内存。
> **定期删除**：每隔一段时间随机抽查一部分设置了过期时间的 key，删掉过期的。抽查而不是全扫，是为了控制 CPU 占用。
>
> **两者结合的原因**：单用惰性会内存泄漏，单用定期会 CPU 开销大或者清理不及时。
>
> **内存淘汰（maxmemory-policy）**，常用几个：
> - `noeviction`：默认，内存满了写入直接报错；
> - `allkeys-lru`：所有 key 里淘汰最近最少使用的（**缓存场景最常用**）；
> - `allkeys-lfu`：淘汰访问频率最低的（Redis 4.0+，比 LRU 更能保护长期热点）；
> - `volatile-lru` / `volatile-ttl`：只在设置了过期时间的 key 里淘汰；
> - `allkeys-random`：随机淘汰。
>
> 选型上：**纯缓存用 `allkeys-lru`**；如果 Redis 里既有缓存又有不能丢的数据（比如我项目里的库存），应该用 **`volatile-lru` 并且给持久数据不设 TTL**，防止把关键数据淘汰掉。

## 第十轮：Spring / Spring Boot

### Q112. 讲一下 Spring 的 IOC 和 AOP。

> **IOC（控制反转）**：对象的创建和依赖关系的维护交给 Spring 容器，而不是程序员自己 `new`。好处是**解耦**——类只依赖接口，具体实现由容器注入。
> 实现方式是 **DI（依赖注入）**，有三种：构造器注入、setter 注入、字段注入。**我现在都用构造器注入**（配合 Lombok 的 `@RequiredArgsConstructor`），因为能保证依赖不可变（`final`）、方便单元测试、也避免循环依赖。
>
> **AOP（面向切面编程）**：把**横切关注点**（日志、事务、权限、限流）从业务代码里抽出来，统一处理。
> 核心概念：**切面（Aspect）、连接点（JoinPoint）、切点（Pointcut）、通知（Advice）、织入（Weaving）**。
> 五种通知：`@Before`、`@After`、`@AfterReturning`、`@AfterThrowing`、`@Around`。
>
> **我项目里的实际应用**：`RateLimitAspect` 就是标准的 AOP 实践——自定义 `@RateLimit` 注解 + `@Around` 环绕通知，在方法执行前做限流判断，业务方法完全不用关心限流逻辑。**这就是 AOP 的价值：业务代码只写业务**。

---

### Q113. Spring AOP 的实现原理？JDK 动态代理和 CGLIB 的区别？

> Spring AOP 底层是**动态代理**，在运行时生成代理对象，代理对象里插入切面逻辑。
>
> **JDK 动态代理**：基于**接口**。要求目标类必须实现接口，生成的代理类实现了同样的接口。通过 `InvocationHandler` 的 `invoke` 方法织入逻辑。
> **CGLIB**：基于**继承**。通过继承目标类并覆写方法来实现代理，所以**不能代理 final 类和 final 方法**。
>
> **Spring Boot 2.x 之后默认全部用 CGLIB**（Spring 4 之前是"有接口用 JDK，没接口用 CGLIB"）。原因是用 CGLIB 更简单——不需要强制要求接口，而且能避免"注入接口 vs 注入实现类"带来的类型问题。
> 可以通过 `@EnableAspectJAutoProxy(proxyTargetClass = false)` 切回 JDK 代理。
>
> **局限**：动态代理只能拦截**方法级别**，不能拦截字段访问；而且 `private`、`static`、`final` 方法拦截不到；**同类内部调用也不走代理**（见 Q53）。

### Q114. Bean 的生命周期？

**高频题，要按顺序说清楚：**

> 1. **实例化**：反射调用构造器创建对象；
> 2. **属性填充**：注入依赖（`@Autowired` 就是在这一步处理的）；
> 3. **`Aware` 回调**：如果实现了 `BeanNameAware`、`BeanFactoryAware`、`ApplicationContextAware`，会回调对应方法；
> 4. **`BeanPostProcessor.postProcessBeforeInitialization`**：初始化前的前置处理；
> 5. **`@PostConstruct` / `InitializingBean.afterPropertiesSet` / `init-method`**：初始化方法，按这个顺序执行；
> 6. **`BeanPostProcessor.postProcessAfterInitialization`**：初始化后处理——**AOP 代理就是在这里生成的**；
> 7. **Bean 就绪，可以使用**；
> 8. **`@PreDestroy` / `DisposableBean.destroy` / `destroy-method`**：容器关闭时销毁。
>
> **我项目里的实际例子**：`CacheClient` 里的 `@PreDestroy shutdownPool()`，就是在这个生命周期末尾关闭线程池，避免非守护线程卡住 JVM 退出。`SeckillWarmUpTask` 的 `@PostConstruct init()` 是在第 5 步执行的，应用启动后就立刻预热一次。

### Q115. Spring 循环依赖怎么解决？三级缓存是什么？

> **循环依赖**是 A 依赖 B、B 依赖 A。Spring 通过**三级缓存**解决（只针对**单例 + setter/字段注入**）。
>
> - **一级缓存 `singletonObjects`**：存完全初始化好的 Bean；
> - **二级缓存 `earlySingletonObjects`**：存**提前暴露的、还没填充属性的半成品 Bean**；
> - **三级缓存 `singletonFactories`**：存生成半成品的工厂（`ObjectFactory`），**主要目的是为了 AOP**——如果这个 Bean 需要代理，工厂返回的是代理对象。
>
> **流程**：A 实例化后，把自己放进三级缓存 → 填充属性时发现需要 B → 创建 B → B 填充属性发现需要 A → 从三级缓存拿到 A 的工厂，生成 A 的早期引用放进二级缓存 → B 完成 → A 完成。
>
> **为什么需要三级而不是两级**：如果只用两级，那 A 的早期引用在实例化后就要立刻放进二级缓存。但如果 A 需要被 AOP 代理，这时还判断不了（代理是在初始化后才生成的）。三级缓存的工厂**把"是否要代理"的决策延后到真正被依赖时才执行**，保证注入的是正确的代理对象。
>
> **解决不了的情况**：**构造器注入的循环依赖**（实例化都完成不了，没法提前暴露）；**原型（prototype）Bean 的循环依赖**。这两种都会直接抛异常。
>
> 顺带说：**Spring Boot 2.6 之后默认禁止循环依赖**，需要显式开启 `spring.main.allow-circular-references=true`。这是好事——**循环依赖通常是设计问题的信号**，应该重构而不是绕过。

### Q116. Spring 事务的传播行为有哪些？

> 常用的七种，重点记前四个：
> - **`REQUIRED`（默认）**：有事务就加入，没有就新建；
> - **`REQUIRES_NEW`**：**总是新建一个事务**，原事务挂起。适合"记录日志不能因为主业务回滚而丢失"这类场景；
> - **`NESTED`**：嵌套事务，用保存点（savepoint）实现，子事务回滚不影响父事务；
> - **`SUPPORTS`**：有就加入，没有就以非事务方式执行；
> - `NOT_SUPPORTED`：以非事务方式执行，挂起当前事务；
> - `MANDATORY`：必须在事务中，否则抛异常；
> - `NEVER`：必须不在事务中，否则抛异常。
>
> **最容易踩的坑**：`REQUIRED` 下，内部方法抛异常被外层 `try-catch` 吞掉后，**事务仍然会被标记为 rollback-only**，导致最终提交时抛 `UnexpectedRollbackException`。要避免就**用 `REQUIRES_NEW`**。

### Q117. `@Transactional` 什么情况下会失效？

**⚠️ 高频陷阱题，几乎必问。**

> 1. **同类内部方法调用**——和 AOP 限流失效是同一个原因，走的是 `this` 不是代理。**最常见的一条。**
> 2. **方法不是 `public`**——Spring AOP 默认只拦截 public 方法。
> 3. **异常被吞掉**——`try-catch` 了异常没往外抛，事务管理器感知不到，不会回滚。
> 4. **异常类型不匹配**——默认**只对 `RuntimeException` 和 `Error` 回滚**，受检异常（`Exception` 的直接子类）不回滚。要回滚得写 `@Transactional(rollbackFor = Exception.class)`。**这一条极容易踩，建议无脑加上 `rollbackFor`。**
> 5. **类没有被 Spring 管理**（没加 `@Component` 等注解），或者**数据库引擎不支持事务**（MyISAM）。
> 6. **事务传播行为设置成了 `NOT_SUPPORTED`**。
> 7. **多线程**——事务信息存在 `ThreadLocal` 里，新线程拿不到父线程的事务。

### Q118. Spring Boot 自动配置的原理？

> 核心是 **`@SpringBootApplication`**，它是个组合注解，包含三个：
> - **`@SpringBootConfiguration`**：本质是 `@Configuration`；
> - **`@ComponentScan`**：扫描当前包及子包的组件；
> - **`@EnableAutoConfiguration`**：**自动配置的开关**。
>
> `@EnableAutoConfiguration` 通过 `@Import(AutoConfigurationImportSelector.class)` 来工作。这个 Selector 会读取所有 jar 包里的 **`META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`** 文件（Spring Boot 2.7 之前是 `spring.factories`），拿到所有候选配置类的全限定名。
>
> 然后**通过条件注解过滤**——`@ConditionalOnClass`（类路径下有没有这个类）、`@ConditionalOnMissingBean`（用户有没有自己定义）、`@ConditionalOnProperty`（配置开关）等，满足条件的才真正生效。
>
> **所以"自动配置"不是无脑全加载，而是"按需加载 + 用户配置优先"**——这也是为什么你只要引入 `spring-boot-starter-data-redis`，`RedisTemplate` 就自动可用了，但你自己定义了一个 `RedisTemplate` Bean，自动配置的就会退让。

### Q119. TCP 三次握手和四次挥手？为什么是三次和四次？

> **三次握手**：
> 1. 客户端发 `SYN`（seq=x），进入 `SYN_SENT`；
> 2. 服务端回 `SYN+ACK`（seq=y, ack=x+1），进入 `SYN_RCVD`；
> 3. 客户端回 `ACK`（ack=y+1），双方进入 `ESTABLISHED`。
>
> **为什么是三次**：核心是**让双方都确认对方的收发能力都正常**，并且**同步双方的初始序列号**。
> 两次不够：服务端发出 `SYN+ACK` 后无法确认客户端收到了。如果客户端的旧连接请求延迟到达，服务端回了 `SYN+ACK` 并建立连接，会白白等待一个不存在的客户端，浪费资源。
>
> **四次挥手**：
> 1. 客户端发 `FIN`，进入 `FIN_WAIT_1`；
> 2. 服务端回 `ACK`，进入 `CLOSE_WAIT`，客户端进入 `FIN_WAIT_2`；
> 3. 服务端把剩余数据发完，发 `FIN`，进入 `LAST_ACK`；
> 4. 客户端回 `ACK`，进入 `TIME_WAIT`，等待 2MSL 后关闭。
>
> **为什么是四次**：**因为 TCP 是全双工的，两个方向的关闭要分别进行**。服务端收到 `FIN` 只表示客户端不再发数据了，但服务端可能还有数据要发，所以 `ACK` 和 `FIN` 不能合并（三次握手时 `SYN+ACK` 可以合并，因为服务端没有额外数据要发）。
>
> **`TIME_WAIT` 为什么要等 2MSL**：一是**保证最后一个 `ACK` 能到达服务端**（丢了的话服务端会重发 `FIN`，客户端还能响应）；二是**让本次连接的残留报文在网络中消失**，避免影响下一个使用相同端口的新连接。

### Q120. `TIME_WAIT` 太多怎么办？`CLOSE_WAIT` 太多呢？

> **`TIME_WAIT` 过多**：说明本机是**主动关闭方**，短连接太多。这是**正常现象**，但如果端口耗尽就会出问题。
> 解决：**用长连接（连接池）减少连接数**（这是根本解法）；开启 `net.ipv4.tcp_tw_reuse` 复用（**只对客户端有效**，且要开启时间戳）；调小 `net.ipv4.tcp_max_tw_buckets`（治标，可能丢连接）。**`tcp_tw_recycle` 已经被废弃了，因为它对 NAT 环境有严重问题。**
>
> **`CLOSE_WAIT` 过多**：这是**代码 bug 的信号**，说明**被动关闭方收到了 `FIN` 但没有调用 `close()`**。通常是**连接没有正确释放**——比如流没关、连接没还回池、异常路径漏了 `finally`。
> **这个只能靠改代码解决**，调内核参数没用。我实习时写的文件服务，所有的流操作都用 try-with-resources，就是为了避免这类问题。

### Q121. TCP 和 UDP 的区别？

| | TCP | UDP |
|---|---|---|
| 连接 | 面向连接 | 无连接 |
| 可靠性 | 可靠（确认、重传、排序） | 不可靠 |
| 传输方式 | 字节流 | 数据报 |
| 头部开销 | 20 字节起 | 8 字节 |
| 速度 | 慢 | 快 |
| 一对多 | 不支持（只能一对一） | 支持广播/多播 |

> **选型**：TCP 用于**要求不丢数据**的场景（HTTP、文件传输、数据库连接）；UDP 用于**要求低延迟、能容忍少量丢包**的场景（视频直播、游戏、DNS 查询）。
>
> **补充**：现在很多低延迟协议是基于 UDP 自己实现可靠性（比如 QUIC），因为**TCP 的队头阻塞问题**——一个包丢了，后面的包即使收到了也要等重传，整个连接卡住。这是 HTTP/3 改用 QUIC（基于 UDP）的重要原因。

### Q122. 在浏览器输入 URL 到页面展示，发生了什么？

> 经典大题，按层次从上到下讲：
> 1. **DNS 解析**：域名 → IP。依次查浏览器缓存、系统 hosts、本地 DNS 服务器、根域名服务器（递归 + 迭代查询）；
> 2. **建立 TCP 连接**：三次握手。如果是 HTTPS，还要 **TLS 握手**（协商加密套件、验证证书、生成会话密钥）；
> 3. **发送 HTTP 请求**：请求行、请求头、请求体；
> 4. **服务端处理**：经过 Nginx 反向代理 → 网关 → 具体服务，执行业务逻辑，可能查缓存、查 DB；
> 5. **返回 HTTP 响应**：状态码 + 响应头 + 响应体；
> 6. **浏览器渲染**：解析 HTML 构建 DOM 树 → 解析 CSS 构建 CSSOM → 合成渲染树 → 布局（Layout）→ 绘制（Paint）→ 合成（Composite）；
> 7. **TCP 四次挥手**（如果是短连接）。
>
> **可以结合自己项目展开**：我做的限流就是在这条链路的第 4 步——请求进入 Spring 之后，被 AOP 切面判断"这个用户在这个时间窗口内的请求数超没超"，超了直接 429 返回，**连业务方法都不会执行**。

### Q123. HTTP 和 HTTPS 的区别？HTTPS 的握手过程？

> **区别**：HTTP 明文传输，HTTPS 在 HTTP 和 TCP 之间加了 **TLS/SSL 层**做加密。默认端口 HTTP 是 80，HTTPS 是 443。HTTPS 需要 CA 证书，有额外的握手开销。
>
> **TLS 握手（简化版）**：
> 1. 客户端发 `ClientHello`，带上支持的 TLS 版本、加密套件、随机数 A；
> 2. 服务端回 `ServerHello`，选定加密套件 + 随机数 B，然后发送**证书**；
> 3. 客户端**验证证书**（是否可信 CA 签发、是否过期、域名是否匹配），验证通过后生成随机数 C，**用证书里的公钥加密后发给服务端**；
> 4. 双方各自用 A + B + C 计算出**会话密钥**（对称密钥）；
> 5. 之后的通信都用这个对称密钥加密。
>
> **为什么用对称加密传数据、非对称加密传密钥**：**非对称加密安全但慢**（RSA 比 AES 慢几个数量级），**对称加密快但密钥分发不安全**。所以用非对称加密安全地交换一个对称密钥，之后用对称密钥传数据，兼顾安全和性能。

### Q124. 进程和线程的区别？协程呢？

> **进程**是**资源分配的基本单位**，有独立的地址空间、文件描述符、内存等。**线程**是**CPU 调度的基本单位**，同一进程内的线程**共享地址空间和资源**，但有独立的栈和程序计数器。
>
> **区别**：进程间通信要 IPC（管道、消息队列、共享内存、Socket），线程间直接共享内存（所以需要同步机制）；进程切换开销大（要换页表、刷 TLB），线程切换开销小；进程隔离性好，一个崩溃不影响别人，线程一个崩了整个进程就完了。
>
> **协程**是**用户态的轻量级线程**，由程序自己调度，不经过操作系统内核。切换成本极低（不涉及内核态切换），可以创建几十万个。Java 21 的**虚拟线程**就是协程的实现。
>
> **实际应用**：我项目里的**异步缓存重建线程池**是一个线程池方案，瓶颈是**线程数量受限于内存**（每个线程 1MB 栈）。如果并发重建的任务量极大，虚拟线程会更合适——因为重建是 IO 密集型（查 DB），虚拟线程在 IO 阻塞时会自动让出载体线程，能用很少的 OS 线程支撑海量任务。

### Q125. IO 多路复用是什么？`select`、`poll`、`epoll` 的区别？

> **IO 多路复用**是**用一个线程同时监听多个文件描述符**，哪个就绪了就处理哪个。这是 Redis、Nginx 高并发的核心基础。
>
> - **`select`**：把 fd 集合从用户态拷贝到内核态，内核遍历检查。**限制是 fd 数量有上限（1024）**，而且每次调用都要全量拷贝和遍历，O(n)。
> - **`poll`**：用链表存 fd，**没有数量限制**了，但仍然要全量遍历，O(n)。
> - **`epoll`**：**内核维护一个红黑树存 fd，一个就绪链表存已触发的事件**。调用时不需要拷贝全量 fd，只返回就绪的那几个，**O(1)**。支持边缘触发（ET）和水平触发（LT）。
>
> **为什么 Redis 用 epoll**：Redis 要同时处理几万个连接，每个连接大部分时间都是空闲的。如果用 select，每次都要遍历几万个 fd，绝大部分是无用的。epoll 只在有事件时才返回，效率高得多。

### Q126. 你遇到过最大的技术困难是什么？怎么解决的？

> 是**缓存重建的 Redisson 锁报错**那次。
>
> 现象是逻辑过期触发重建时，偶尔会抛 `IllegalMonitorStateException`。我一开始以为是锁没释放，在 `finally` 里加了一堆日志，但日志显示 `unlock` 确实执行了。
>
> 后来我去读 Redisson 的源码，才明白**它的锁是记录"哪个线程持有"的**，`tryLock` 和 `unlock` 必须在同一个线程。而我的代码是主线程 `tryLock`、把任务丢给线程池，工作线程去 `unlock`——**线程对不上**。
>
> 解决方案是把**整个"抢锁 + 重建 + 解锁"打包成一个任务提交给线程池**，让加锁和解锁都发生在工作线程内部。
>
> 这件事的收获不只是修了个 bug，而是让我意识到——**很多"偶发的、诡异的"问题，根因是我们对所用工具的假设错了**。我当时默认"锁是全局的，谁都能解"，而 Redisson 的设计是"锁绑定线程"。之后我用任何中间件，都会先去确认它的核心假设是什么。

**⚠️ 这个故事你的代码注释里真实存在，讲起来会非常可信。**

### Q127. 你和同事/同学有过技术分歧吗？怎么处理的？

> 有。做秒杀的时候，我和同学争论过**要不要用 RedLock**。
>
> 他的理由是"RedLock 更安全，不用显得不够专业"。我的理由是我们的场景是缓存重建，**即使极低概率下两个线程同时重建，结果也就是多查一次 DB、多写一次缓存，数据仍然是正确的**——没必要为了一个不影响正确性的场景引入 RedLock 的复杂度（多节点部署、时钟依赖、性能损耗）。
>
> 我的处理方式是**把争论从"哪个技术更好"转成"我们的风险等级是什么"**。我问了他一个问题：*"如果这两个线程真的同时重建了，最坏的结果是什么？"* 他想了想说"就是多查一次库"。这样就达成一致了。
>
> 我的体会是：**技术分歧往往不是技术问题，而是双方对"风险"和"成本"的权重不一样**。把讨论拉回到具体的后果上，比争论技术优劣有效得多。
